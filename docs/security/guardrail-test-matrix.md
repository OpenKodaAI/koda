# Koda Guardrail Test Matrix

This matrix maps the security boundaries agents rely on to adversarial tests.
Every test in `tests/security/` should prove the expected decision, the
presence or absence of execution, canary integrity, and secret redaction when
the scenario involves credentials or process output.

| Background shell | `shell_bg` takes the same path as `shell_execute`: the integration grant and execution policy, the token blocklist, the execution-approval check and the command guard, then the runtime kernel's `ExecuteCommand`. It never spawns a process itself. A command that `shell_execute` refuses, including any command while execution is not approved, gets the same refusal from `shell_bg`; when the runtime kernel is unavailable nothing runs and the handle reports the kernel error. A command that outlives its timeout, or leaves a process holding its output open past it, is stopped by the kernel and reported as timed out with the output read so far; such timeouts do not count against the runtime-kernel circuit breaker. A command that the kernel's own command check or network policy refuses (the shell tools never set `allow_network`, so `curl`, `wget`, `ssh` or an `http://` or `https://` URL are refused) gets the same `Blocked:` answer from both tools and does not count against the breaker either. A kernel that does not answer within the command's timeout plus 5 s is reported as an error and counts against the breaker. `shell_kill` cancels the kernel call, and the kernel then kills every process still in the command's process group. A process that leaves the group (`setsid`, a daemonizing fork) is not covered: the command guard is a guard, not a sandbox (ADR-010). Process handles are scoped to the owning user, and each `shell_bg` call drops the handles of commands that finished more than 10 minutes earlier. | `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_handle_is_user_scoped`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_denies_what_shell_execute_denies`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_fails_closed_without_execution_approval`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_is_held_by_the_integration_grant_gate_that_holds_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_is_held_by_the_execution_policy_rule_that_holds_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_allowed_by_policy_reaches_the_approval_gate_of_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_runs_allowed_command_through_runtime_kernel`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_gets_the_answer_of_shell_execute_when_the_runtime_kernel_refuses`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_kill_leaves_no_process_in_its_group`, `tests/test_services/test_shell_tools.py::TestBackgroundTimeoutsThroughRuntimeKernelClient`, `rust/koda-runtime-kernel/src/commands.rs` (`dropping_execute_shell_command_kills_its_process_group`, `a_process_holding_the_output_open_is_stopped_at_the_timeout`, `a_process_that_left_the_group_cannot_hold_the_reply`), and against a freshly built kernel binary in the pr-quality `runtime-kernel-live` job (locally opt-in: `KODA_TEST_RUNTIME_KERNEL_BIN` or `KODA_TEST_RUNTIME_KERNEL=1`) `tests/integration/test_runtime_kernel_shell_live.py` |
| File operations | The Telegram file commands (`/cat`, `/file`, `/ls`, `/write`, `/edit`, `/rm`, `/mkdir`) and the agent `file_*` tools share one resolver (`koda/utils/files.py::resolve_work_path`), so a path gets the same decision on both: relative paths resolve against the work directory, never the process CWD; the resolved path, symlinks included, must stay inside the workdir; and secret files stay blocked by name on both (`koda/utils/files.py::secret_file_refusal`), for the blocked extensions (`prod.env`, `server.pem`), for `.env` dotfiles (`.env`, `.env.local`), and for the credential stores that the provider and developer CLIs keep in HOME (`FILEOPS_BLOCKED_CREDENTIAL_PATHS`: the `.ssh/`, `.gnupg/`, `.aws/`, `.azure/` and `.config/gcloud/` directories with everything below them, and `.claude/.credentials.json`, `.codex/auth.json`, `.gemini/oauth_creds.json`, `.config/gh/hosts.yml`, `.docker/config.json`, `.kube/config`, `.git-credentials`, `.netrc`, `_netrc`, `.pgpass`, `.npmrc` and `.pypirc`). That last list matters in the default Docker layout, where the work dir is the runtime HOME those CLIs share. Only these names are recognised: a credential saved under any other name in the work dir is readable like any other file. The file tools do not create such a name themselves: `file_move` refuses a move or rename that would take a store out of the name that blocks it (`koda/utils/files.py::secret_move_refusal`), so renaming `.codex`, `.gemini`, `.config`, `.config/gh`, `.docker` or `.kube`, whose stores are recognised by that parent's name, is refused, while a directory whose secrets keep a refused name where it lands (a project holding `.env`, `.codex` moved into `backup/`) still moves. Committed templates whose final extension is `.example`, `.sample`, `.template` or `.dist` (`.env.example`, `.env.local.example`) are not secrets and stay readable and editable on both, unless they link to a blocked file. The file tools also refuse paths inside a sensitive system directory (`SENSITIVE_DIRS`, matched as written and resolved, so `/var/run` also covers `/run`) and, in every work dir, paths inside the control-plane state directory (`STATE_ROOT_DIR/control_plane`, which holds the master key and the bootstrap code, and outside Docker sits inside the default work dir `~`), except the sensitive directories that one of Koda's own runtime roots is configured under, when the work dir is that runtime root or below it (`koda/utils/workdir.py::sensitive_dir_for`). The runtime roots are `RUNTIME_ROOT_DIR`, `RUNTIME_EPHEMERAL_ROOT` and `DEFAULT_WORK_DIR`, as configured (`koda/utils/workdir.py::runtime_roots`): in the Docker layout `/var/lib/koda/runtime`, the runtime `HOME=/var/lib/koda/runtime/home` (the default work dir) and the paths inside them stay usable under `/var/lib`. Every other sensitive directory stays refused, including one that a work dir reaches only through a symlink, such as a validated work dir later replaced with a symlink into `/etc`, a link inside a runtime root to another directory under `/var/lib`, or a runtime root that now resolves into a sensitive directory it is not configured under. The commands skip that check, so the two differ only for a path inside a sensitive directory that is not waived: in a work dir that contains one, such as `/`, `file_read /etc/hosts` is refused and `/cat etc/hosts` reads the file, and the same holds in a work dir that resolves into one after it was validated, such as one replaced with a symlink. `/setdir`, its directory buttons, `agent_set_workdir`, `job_create`, workspace roots and queued and scheduled tasks all use the same work-dir check (`koda/utils/workdir.py::validate_work_dir`): it refuses a work dir under a sensitive directory or the control-plane state directory, and accepts Koda's runtime roots and the directories below them with the waiver above, so in the Docker layout the default work dir, a directory inside it and the runtime root are valid work dirs and a scheduled run there is not refused. `file_grep` skips every secret file, does not descend into a sensitive directory (other than the waived ones) or a credential-store directory, and reads a file symlink only when the full resolver allows its target and the target is inside the search root, so a link inside a granted subtree to a file elsewhere in the work dir is skipped. A fileops integration grant with `allowed_paths` sees the same resolved path on both surfaces. Each file command takes its path from `koda/utils/files.py::file_command_path` (the first argument for `/write` and `/edit`, every argument joined by a space for the others, never shell-split or unquoted, and `.` for `/ls` alone), and the approval layer (`koda/utils/approval.py::with_approval`) checks the grant on that same path, resolved, when the command arrives; `/file` and `/ls` are gated there like `/cat`, as the read actions `fileops.file` and `fileops.ls`. A confirmation (`/rm`, `/write`, `/edit`, `/mkdir`) is pinned to that resolved path: when it is approved, `dispatch_approved_operation` runs the gate again on the same parsed path, against the work dir current at that moment, and runs the handler only if the path still passes it, still resolves to the path the confirmation was for, and is still covered by the grant. So a work dir change between the request and the approval (`/setdir`, `agent_set_workdir`, a queued task), a link on the path repointed in between, or a narrowed grant refuses the approval (`Not run: ...`, or the gate's own refusal) and touches nothing. The gate, that re-check and the handlers read the work dir the same way (`koda/utils/files.py::file_command_work_dir`), as stored and not stripped, so a work dir whose name ends in a space is the one the grant checks; with no work dir set (or a blank one) the commands refuse to run instead of resolving the path against the process CWD. The file tools pass each `path`, `source` and `destination` as the absolute, symlink-resolved path it names under the work dir (`koda/utils/files.py::work_path_location`). So `/cat src/main.py` and `file_read src/main.py` are both granted under `<work>/src`, `<work>/src/../.git/config` and `src/x /../../.git/config` are refused by both, and `/ls` alone and `file_list` without a `path` are both checked against the work dir. `allowed_paths` entries and the call path are both compared in canonical form, `~` expanded, lexically normalized and symlink-resolved symlink, such as a symlinked project dir or macOS `/tmp`, still covers the paths below it, a path written as `<grant root>/../etc/x` or through a link inside the grant root is compared where it lands, and a relative entry or call path covers nothing. `file_search` and `file_grep` without a `path` are checked against the work dir they read, and `file_move` must have both its source and its destination inside the grant. | `tests/security/test_guardrail_adversarial_suite.py::test_fileops_rejects_symlink_escape_and_sensitive_extensions`,
