# Koda Guardrail Test Matrix

This matrix maps the security boundaries agents rely on to adversarial tests.
Every test in `tests/security/` should prove the expected decision, the
presence or absence of execution, canary integrity, and secret redaction when
the scenario involves credentials or process output.

| Surface | Guardrail | Evidence Target |
| --- | --- | --- |
| Shell | Destructive commands, env exfiltration, reverse shells, and forbidden tokens are blocked before execution. | `tests/security/test_guardrail_adversarial_suite.py::test_shell_destructive_commands_do_not_touch_canary` |
| Background shell | Process handles are scoped to the owning user. | `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_handle_is_user_scoped` |
| File operations | Paths must remain inside the workdir and sensitive extensions stay blocked. | `tests/security/test_guardrail_adversarial_suite.py::test_fileops_rejects_symlink_escape_and_sensitive_extensions` |
| Browser | Private-network downloads honor the global kill switch, redirects are blocked before the browser follows them, and uploads cannot read files outside the workdir. | `tests/security/test_guardrail_adversarial_suite.py::test_browser_private_download_respects_global_kill_switch`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_download_blocks_private_redirect_before_network`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_upload_rejects_path_outside_workdir` |
| HTTP/SSRF | Agent web tools, the link analyzer, artifact ingestion, and the control-plane link preview (`koda/services/http_client.py`) only reach public unicast addresses unless a private-network grant (`allow_private_network`) applies: private, loopback, link-local, unspecified (`0.0.0.0`, `::`), reserved, multicast, and `100.64.0.0/10` shared space are blocked, and IPv4-mapped / NAT64 IPv6 addresses are judged by the IPv4 address they embed. The host is checked as aiohttp parses it (`yarl.URL(url).raw_host`, IDNA per UTS-46), so a non-ASCII host cannot pass the check as a DNS name and then be connected to as an IP literal. The connection is pinned to the validated addresses by a connect-time resolver, so DNS rebinding between the check and the connect cannot reach a private host, and every redirect (including web search) is re-checked before it is followed. Fake-IP DNS setups (Clash, sing-box or Surge in fake-ip mode answer from `198.18.0.0/15`) and CGNAT or Tailscale destinations (`100.64.0.0/10`) are therefore treated as non-public: such a deployment sees `private/reserved` errors until it uses real DNS or grants private-network access. The link analyzer never hands a user URL to yt-dlp, which resolves DNS and follows redirects outside this guard: only URLs whose host is YouTube are treated as videos, and yt-dlp receives a `https://www.youtube.com/watch?v=<id>` URL built from the validated video ID. Artifact ingestion follows the same rule: yt-dlp only receives a watch URL rebuilt from a validated YouTube, Vimeo or Dailymotion video ID, never the fetched URL. | `tests/test_services/test_http_client.py::test_fetch_url_cannot_reach_local_service_via_unspecified_address`, `tests/test_services/test_http_client.py::test_fetch_url_pins_connection_against_dns_rebinding`, `tests/test_services/test_http_client.py::test_fetch_url_blocks_redirect_to_unspecified_address`, `tests/test_services/test_http_client.py::test_entry_points_cannot_reach_loopback_through_idna_mapped_host`, `tests/test_services/test_http_client.py::test_private_network_grant_reaches_internal_hostnames`, `tests/test_services/test_link_analyzer.py::TestYtDlpOnlySeesCanonicalYoutubeUrls`, `tests/test_services/test_artifact_ingestion.py::TestYtDlpOnlySeesCanonicalWatchUrls`, plus MCP HTTP redirect tests below. |
| OpenAI-compatible providers | A guarded base URL (the vendor endpoint of a profile not flagged `allow_private_base_url`) must pass the same address check; its connections use the connect-time resolver and do not follow redirects, so an unfollowed 3xx is reported as an HTTP error. Any configured `*_API_BASE_URL` other than the vendor endpoint, whether it comes from the control plane or from `.env` / the process environment, is an operator override and, like a profile flagged `allow_private_base_url` (the local llama.cpp and MLX runtimes), may reach private hosts: its connections are not pinned by the connect-time resolver and redirects are followed. | `tests/test_services/test_openai_compatible_runner.py::TestProviderRequestsStayOnPublicAddresses`, `tests/test_services/test_openai_compatible_runner.py::TestProcessEnvBaseUrlIsAnOperatorOverride` |
| MCP HTTP | Remote MCP transports judge the host with the shared classifier above (as aiohttp parses it) during construction and on every redirect, connect only to the addresses the guard checked, ignore `*_proxy`, and refuse a redirect to another origin, so credential headers never leave the configured server. `MCP_ALLOWED_PRIVATE_NETWORKS` (CIDRs, for example a Tailscale tailnet, which needs its IPv6 range `fd7a:115c:a1e0::/48` as well as `100.64.0.0/10`, because one DNS answer that is neither public nor granted refuses the host) is the only private-network grant; it never covers loopback, link-local, unspecified or multicast addresses, nor the cloud metadata addresses outside link-local (`100.100.100.200`, `fd00:ec2::254`), and granted connections are still pinned at connect time. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_http_redirect_to_private_destination_is_blocked`, `tests/security/test_outbound_fetch_guard.py` (`mcp_http` cases, `test_mcp_cross_origin_redirect_is_refused`, `test_mcp_ignores_proxy_environment`, `test_tailscale_mcp_server_needs_an_explicit_grant`, `test_documented_tailscale_grant_admits_dual_stack_nodes`, `test_mcp_grant_never_covers_loopback_metadata_or_unspecified`, `test_mcp_server_on_a_granted_private_network_round_trips`) |
| Other outbound fetches | Generated-image downloads, the OpenAI-compatible provider API-key verifier, Ollama (chat in cloud and local mode, the local connection check, the control plane's model catalog) and the control plane's calls to the agent runtime API go through `guarded_urlopen` in `koda/services/http_client.py`: http and https only, no `*_proxy`, no redirect to another origin (the verifier's health probe follows no redirect at all). Third-party destinations reach public addresses only, pinned at connect time, so `0.0.0.0`, IPv4-mapped IPv6, `100.64.0.0/10`, NAT64 and DNS rebinding are refused. Endpoints the operator configured (local Ollama, a non-vendor provider base URL, the runtime API) hold a private-network grant for their own origin and keep working. Not covered yet: MCP OAuth discovery, registration and token requests, the local llama.cpp/MLX runtime supervisor, and the API-key checks against fixed vendor hosts (Claude, Codex, Gemini, ElevenLabs, Ollama Cloud) still use `urllib.request.urlopen`. | `tests/security/test_outbound_fetch_guard.py` (per-path probes, including `test_public_path_cross_origin_redirect_is_refused` and `test_public_path_ignores_proxy_environment` over TLS for the https paths, and the shared-client cases) |
| MCP stdio/custom | Custom command/env registration rejects obvious host-code-execution escapes and malformed argv values. | `tests/test_services/test_custom_mcp_registry.py` |
| MCP control plane | Agent connection overrides cannot smuggle unsafe commands, malformed argv, unsafe URLs, forbidden env names, non-string env values, or null-as-secret values into runtime config. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_agent_connection_rejects_unsafe_overrides`, `tests/test_control_plane_mcp.py::TestMCPAgentConnections::test_null_env_values_are_ignored_not_stored_as_literal_secret`, `tests/test_control_plane_mcp.py::TestMCPAgentConnections::test_env_values_reject_non_string_values` |
| MCP capabilities | Blocked resources are hidden whether policy stores the URI or the canonical URI hash. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_resource_blocking_accepts_uri_or_hash_policy_names` |
| Execution policy | Unknown tools fail closed, read-only tasks deny writes, approval grants replay only the authorized action. | `tests/security/test_guardrail_adversarial_suite.py::test_execution_policy_unknown_tool_fails_closed_with_evidence`, existing `tests/test_services/test_execution_policy.py` |
| Provider/runtime env | Tool subprocess env is allowlisted and fails safe if the security RPC is unavailable. | `tests/security/test_guardrail_adversarial_suite.py::test_tool_subprocess_env_drops_secret_canary` |
| Worker and runtime-kernel processes | Both make themselves non-dumpable and set `RLIMIT_CORE` to 0, or refuse to start: the kernel first thing in `main`, the worker in the first statement of `koda/__main__.py`. From then on, a same-uid process without `CAP_SYS_PTRACE` gets `Permission denied` on their `/proc/<pid>/environ`, and no core file is written. The kernel still spawns, reaps and terminates workers, and they still die with it. Residual: during a worker's startup window (Python startup, before `koda/__main__.py` runs) a same-uid process can still read the worker's environment, and it can open a new window by killing the worker, which the kernel restarts. Only ADR-002's L2 (Landlock) confinement closes it, once AG-14 (provider CLIs, governed shell and git that the worker starts), AG-15 (the kernel's `StartTask` and `ExecuteCommand` children) and AG-16 (MCP stdio servers, media tools and chromium) have all shipped. It stays open under `RUNTIME_CONFINEMENT=off`, and for class U processes (MCP stdio servers, media tools, chromium) on a host without L2, which still run unconfined with only a health warning; see `docs/operations/hardening.md`. | `tests/security/test_process_hygiene.py::test_same_uid_sibling_cannot_read_worker_environ`, `tests/security/test_process_hygiene.py::test_entrypoint_makes_worker_non_dumpable_with_core_dumps_off`, `rust/koda-runtime-kernel/tests/process_hygiene.rs` |
| Policy engine | Ingest/spend wrappers have explicit tests for deny, hard stop, and the configured outage fallback behavior. | Existing `tests/test_policy_engine_client.py` |

When a new agent-facing tool or MCP capability is added, update this document
in the same change as the policy/test coverage.
