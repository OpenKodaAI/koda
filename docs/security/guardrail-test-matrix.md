# Koda Guardrail Test Matrix

This matrix maps the security boundaries agents rely on to adversarial tests.
Every test in `tests/security/` should prove the expected decision, the
presence or absence of execution, canary integrity, and secret redaction when
the scenario involves credentials or process output.

| Surface | Guardrail | Evidence Target |
| --- | --- | --- |
| Shell | Destructive commands, env exfiltration, reverse shells, and forbidden tokens are blocked before execution. | `tests/security/test_guardrail_adversarial_suite.py::test_shell_destructive_commands_do_not_touch_canary` |
| Git tools | A model-supplied `ref`, branch `name`, `target`, `remote`, `branch` or `start_point` that starts with `-` is rejected before git runs, so it cannot be parsed as an option. The handlers also pass these values after `--end-of-options` where git honours it (`git checkout` reads the marker as a pathspec, and `git pull` hands its operands to `git fetch` without it, so for those two the dash check is the guard). `--output`, `--receive-pack`, `--upload-pack` and `--exec` are refused in any position, including their `=value` forms and the abbreviations git accepts, such as `--outp` or `--receive`. | `tests/test_services/test_git_tools.py::TestGitOptionInjectionProbes`, `tests/test_services/test_git_tools.py::TestGitToolsAgainstRealGit`, `tests/test_services/test_git_tools.py::TestValidateGitArgs` |
| Background shell | `shell_bg` takes the same path as `shell_execute`: the integration grant and execution policy, the token blocklist, the execution-approval check and the command guard, then the runtime kernel's `ExecuteCommand`. It never spawns a process itself. A command that `shell_execute` refuses, including any command while execution is not approved, gets the same refusal from `shell_bg`; when the runtime kernel is unavailable nothing runs and the handle reports the kernel error. A command that outlives its timeout, or leaves a process holding its output open past it, is stopped by the kernel and reported as timed out with the output read so far; such timeouts do not count against the runtime-kernel circuit breaker. A command that the kernel's own command check or network policy refuses (the shell tools never set `allow_network`, so `curl`, `wget`, `ssh` or an `http://` or `https://` URL are refused) gets the same `Blocked:` answer from both tools and does not count against the breaker either. A kernel that does not answer within the command's timeout plus 5 s is reported as an error and counts against the breaker. `shell_kill` cancels the kernel call, and the kernel then kills every process still in the command's process group. A process that leaves the group (`setsid`, a daemonizing fork) is not covered: the command guard is a guard, not a sandbox (ADR-010). Process handles are scoped to the owning user, and each `shell_bg` call drops the handles of commands that finished more than 10 minutes earlier. | `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_handle_is_user_scoped`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_denies_what_shell_execute_denies`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_fails_closed_without_execution_approval`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_is_held_by_the_integration_grant_gate_that_holds_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_is_held_by_the_execution_policy_rule_that_holds_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_allowed_by_policy_reaches_the_approval_gate_of_shell_execute`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_runs_allowed_command_through_runtime_kernel`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_gets_the_answer_of_shell_execute_when_the_runtime_kernel_refuses`, `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_kill_leaves_no_process_in_its_group`, `tests/test_services/test_shell_tools.py::TestBackgroundTimeoutsThroughRuntimeKernelClient`, `rust/koda-runtime-kernel/src/commands.rs` (`dropping_execute_shell_command_kills_its_process_group`, `a_process_holding_the_output_open_is_stopped_at_the_timeout`, `a_process_that_left_the_group_cannot_hold_the_reply`), and against a freshly built kernel binary in the pr-quality `runtime-kernel-live` job (locally opt-in: `KODA_TEST_RUNTIME_KERNEL_BIN` or `KODA_TEST_RUNTIME_KERNEL=1`) `tests/integration/test_runtime_kernel_shell_live.py` |
| File operations | The Telegram file commands (`/cat`, `/file`, `/ls`, `/write`, `/edit`, `/rm`, `/mkdir`) and the agent `file_*` tools share one resolver (`koda/utils/files.py::resolve_work_path`), so a path gets the same decision on both: relative paths resolve against the work directory, never the process CWD; the resolved path, symlinks included, must stay inside the workdir; and secret files stay blocked by name on both (`koda/utils/files.py::secret_file_refusal`), for the blocked extensions (`prod.env`, `server.pem`), for `.env` dotfiles (`.env`, `.env.local`), and for the credential stores that the provider and developer CLIs keep in HOME (`FILEOPS_BLOCKED_CREDENTIAL_PATHS`, which refuses exactly the `.ssh/`, `.gnupg/`, `.aws/`, `.azure/`, `.config/gcloud/`, `.claude/backups/`, `.claude/daemon/auth/` and `.config/anthropic/credentials/` directories with everything below them, and the files `.claude/.credentials.json`, `.codex/auth.json`, `.gemini/oauth_creds.json`, `.gemini/google_accounts.json`, `.gemini/mcp-oauth-tokens.json`, `.claude.json`, `.claude-staging-oauth.json`, `.claude-local-oauth.json`, `.claude-custom-oauth.json`, `.claude/.config.json`, `.device-keys.json`, `.claude/hfi-auth.json`, `.claude/remote/.oauth_token`, `.claude/remote/.api_key`, `.claude/remote/.session_ingress_token`, `.config/gh/hosts.yml`, `.docker/config.json`, `.kube/config`, `.git-credentials`, `.netrc`, `_netrc`, `.pgpass`, `.npmrc` and `.pypirc`). Each file entry also refuses the copies a CLI writes of that file, which hold the same secret (`koda/config.py::FILEOPS_CREDENTIAL_COPY_SUFFIXES`): its name followed by `.backup`, `.corrupted` or `.tmp` and, optionally, a dot and any further suffix, wherever the entry matches, so `.claude.json.backup`, `.claude.json.backup.<ts>`, `.claude.json.corrupted.<ts>` and `.claude.json.tmp.<hex>` are refused in any directory, `.claude/.config.json.tmp.<hex>` beside the legacy config and `.codex/auth.json.tmp.<hex>` beside the Codex login, while `.claude.json.example` and `.claude.json.backupx` stay readable. The provider CLI logins in that list (`.claude/.credentials.json`, `.codex/auth.json` and the three `.gemini/` files) are the files disconnecting a provider deletes in each CLI's config dir under HOME, from one source (`koda/config.py::PROVIDER_CLI_CREDENTIAL_FILES`). The other Claude Code entries are the other files that hold a Claude Code credential in HOME with `CLAUDE_CONFIG_DIR` unset, as the pinned CLI (`packages/provider-clis`, 2.1.325) names them, including every Claude Code and Anthropic path on the CLI's own list of credential files (`.claude/daemon/auth`, `.claude/hfi-auth.json`, `.config/anthropic/credentials`), from one source too (`koda/config.py::CLAUDE_CODE_CREDENTIAL_PATHS`): its global config `~/.claude.json`, which holds the /login managed API key (`primaryApiKey`) and the MCP servers' env and headers and sits in the native default work dir `~`, the same file for another OAuth environment (`.claude-<env>-oauth.json`, `-custom-oauth` with `CLAUDE_CODE_CUSTOM_OAUTH_URL`) and the legacy `.claude/.config.json` the CLI still reads, each with its copies (refused as copies, above: `<name>.backup` beside it, which the CLI recovers it from, `<name>.backup.<ts>` and `<name>.corrupted.<ts>` in its config dir's `backups/`, which is `$CLAUDE_CONFIG_DIR/backups/` where that is set, and the temp copy `<name>.tmp.<hex>` it writes through, which a crash mid-write leaves beside it), and `.claude/backups/` as a whole; the device private keys it keeps in its config dir where no keychain holds them (`.device-keys.json`); the background sessions' auth snapshots and socket tokens (`.claude/daemon/auth/`); the HFI auth file an earlier CLI wrote, which the pinned one never writes and only deletes once it is older than its cleanup period (`.claude/hfi-auth.json`); a remote session's OAuth token, API key and session ingress token (`.claude/remote/`, which the CLI keeps at a fixed path in a remote session's home, only with `CLAUDE_CODE_REMOTE` set); and the Anthropic profile store in its default location (`.config/anthropic/credentials/`: each profile's user OAuth tokens in `<profile>.json`, whose access and refresh token the CLI rewrites on every refresh, and the federation token cache `federation/`). The CLI takes its profile config dir from `ANTHROPIC_CONFIG_DIR`, else `$XDG_CONFIG_HOME/anthropic`, else `~/.config/anthropic`, and the federation cache from `CLAUDE_CODE_FEDERATION_CACHE_DIR` where that is set; where the process's environment names one of those, the credentials dir there is a protected directory (below), for each one the environment names, whichever of them a CLI uses. Disconnecting the provider does not delete those, since the global config is also the operator's settings and project list. The CLI's other keys (`.claude/daemon/control.key`, `.claude/daemon/pipe.key`, `.claude/sessions/*.key`) are refused by their `.key` extension, and its login `.credentials.json`, which also holds the MCP servers' OAuth tokens, by its `.credentials` stem wherever it sits. Where the environment moves that dir out of HOME under another name (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, from one source too: `koda/config.py::PROVIDER_CLI_CONFIG_DIR_ENV_KEYS`), the logout deletes those files there as well, and the file layer refuses that whole dir (a protected directory, below), so a credential file Koda's own logout knows is refused wherever the process's environment puts it. That last list matters in the default Docker layout, where the work dir is the runtime HOME those CLIs share. Only these names are recognised: a credential saved under any other name in the work dir is readable like any other file. The file tools do not create such a name themselves: `file_move` refuses a move or rename that would take a store out of the name that blocks it (`koda/utils/files.py::secret_move_refusal`), so renaming `.codex`, `.gemini`, `.config`, `.config/gh`, `.docker` or `.kube`, whose stores are recognised by that parent's name, is refused, while a directory whose secrets keep a refused name where it lands (a project holding `.env`, `.codex` moved into `backup/`) still moves. Committed templates whose final extension is `.example`, `.sample`, `.template` or `.dist` (`.env.example`, `.env.local.example`) are not secrets and stay readable and editable on both, unless they link to a blocked file. The file tools also refuse paths inside a sensitive system directory (`SENSITIVE_DIRS`, matched as written and resolved, so `/var/run` also covers `/run`) and, in every work dir, paths inside the protected directories that hold Koda's or a provider CLI's credentials (`koda/utils/workdir.py::protected_dirs`): the control-plane state directory (`STATE_ROOT_DIR/control_plane`, which holds the master key and the bootstrap code, and outside Docker sits inside the default work dir `~`), the browser's saved sessions of every chat scope (`browser_sessions` in `BROWSER_SESSION_DIR`, or else in `IMAGE_TEMP_DIR`, by default `RUNTIME_EPHEMERAL_ROOT/image-scratch/browser_sessions`, with each session's cookies and localStorage), and the provider CLI config dirs that `CLAUDE_CONFIG_DIR` and `CODEX_HOME` name where the process's environment sets them (the CLI's login, settings and session transcripts), and the Anthropic profile credential dirs that the environment names (`koda/utils/workdir.py::anthropic_profile_credential_dirs`: `$ANTHROPIC_CONFIG_DIR/credentials`, `$XDG_CONFIG_HOME/anthropic/credentials` and `$CLAUDE_CODE_FEDERATION_CACHE_DIR`, each where it is set). These directories are recognised by their location, not their name, and are compared ignoring case (`koda/utils/workdir.py::protected_dir_for`), as the credential stores are: on a case-insensitive filesystem such as the macOS default, `~/.KODA-STATE/control_plane/bootstrap.txt` opens the bootstrap code, and `os.path.realpath` keeps the case it is given, so that path is refused as the state dir, and so is `file_move .KODA-STATE state-old`. `file_move` keeps them in place (`koda/utils/files.py::protected_move_refusal`): it refuses a move whose source is, or contains, a protected directory, since moving `.koda-state`, `image-scratch` or the parent of `CLAUDE_CONFIG_DIR` or `CODEX_HOME` would put the bootstrap code, the saved cookies or the CLI login at a path no check recognises, where `file_read` would return them; and it refuses a move whose destination (inside an existing destination directory, the path the source lands at) is, contains or lies inside a protected directory, since that would put the moved data where Koda or the CLI reads it from, such as a planted bootstrap code or browser session. A move that holds no protected directory still works, also beside one or into its parent (`.koda-state/logs` to `logs-old`, `notes.txt` into `.koda-state`). A worker reads those two variables from its own environment, that is the agent's environment, which the supervisor passes on, and the install's `.env`, which the worker loads; the supervisor does not copy them from its own environment: the compose files set `CLAUDE_CONFIG_DIR=/var/lib/koda/runtime/claude-config` for the app container only, so a worker there refuses that directory only when the agent's environment sets `CLAUDE_CONFIG_DIR` too, and otherwise a work dir at `RUNTIME_EPHEMERAL_ROOT` reaches the control plane's Claude Code config there (its `.credentials.json`, its `.claude.json` with every copy of it, also the timestamped and corrupted ones in its `backups/`, and its `.device-keys.json` stay refused by extension or name; its `daemon/auth/`, `hfi-auth.json`, a legacy `.config.json` and that one's copies do not, since those entries name them below `.claude`). The protected directories are never waived; the other sensitive directories are, except the sensitive directories that one of Koda's own runtime roots is configured under, when the work dir is that runtime root or below it (`koda/utils/workdir.py::sensitive_dir_for`). The runtime roots are `RUNTIME_ROOT_DIR`, `RUNTIME_EPHEMERAL_ROOT` and `DEFAULT_WORK_DIR`, as configured (`koda/utils/workdir.py::runtime_roots`): in the Docker layout `/var/lib/koda/runtime`, the runtime `HOME=/var/lib/koda/runtime/home` (the default work dir) and the paths inside them stay usable under `/var/lib`. Every other sensitive directory stays refused, including one that a work dir reaches only through a symlink, such as a validated work dir later replaced with a symlink into `/etc`, a link inside a runtime root to another directory under `/var/lib`, or a runtime root that now resolves into a sensitive directory it is not configured under. The commands skip the `SENSITIVE_DIRS` part of that check but never the protected directories (`koda/utils/workdir.py::protected_dir_for`): `/cat`, `/file`, `/ls`, `/write`, `/edit`, `/rm` and `/mkdir` refuse every path inside them as the file tools do, so an allowed Telegram user who is not the owner cannot read, list or change the bootstrap code, a saved browser session or a CLI login kept there. So the two differ only for a path inside a sensitive directory that is not waived: in a work dir that contains one, such as `/`, `file_read /etc/hosts` is refused and `/cat etc/hosts` reads the file, and the same holds in a work dir that resolves into one after it was validated, such as one replaced with a symlink. `/setdir`, its directory buttons, `agent_set_workdir`, `job_create`, workspace roots and queued and scheduled tasks all use the same work-dir check (`koda/utils/workdir.py::validate_work_dir`): it refuses a work dir under a sensitive directory or a protected directory, and accepts Koda's runtime roots and the directories below them, other than the protected ones, with the waiver above, so in the Docker layout the default work dir, a directory inside it and the runtime root are valid work dirs and a scheduled run there is not refused, while `image-scratch/browser_sessions` below the runtime root is not a work dir. `file_search` and `file_grep` do not descend into a hidden directory, a sensitive directory (other than the waived ones), a protected directory or a credential-store directory (`koda/services/tool_dispatcher.py::_searchable_subdirs`), so neither names nor reads a file there; `file_grep` also skips every secret file, and reads a file symlink only when the full resolver allows its target and the target is inside the search root, so a link inside a granted subtree to a file elsewhere in the work dir is skipped. A fileops integration grant with `allowed_paths` sees the same resolved path on both surfaces. Each file command takes its path from `koda/utils/files.py::file_command_path` (the first argument for `/write` and `/edit`, every argument joined by a space for the others, never shell-split or unquoted, and `.` for `/ls` alone), and the approval layer (`koda/utils/approval.py::with_approval`) checks the grant on that same path, resolved, when the command arrives; `/file` and `/ls` are gated there like `/cat`, as the read actions `fileops.file` and `fileops.ls`. A confirmation (`/rm`, `/write`, `/edit`, `/mkdir`) is pinned to that resolved path: when it is approved, `dispatch_approved_operation` runs the gate again on the same parsed path, against the work dir current at that moment, and runs the handler only if the path still passes it, still resolves to the path the confirmation was for, and is still covered by the grant. So a work dir change between the request and the approval (`/setdir`, `agent_set_workdir`, a queued task), a link on the path repointed in between, or a narrowed grant refuses the approval (`Not run: ...`, or the gate's own refusal) and touches nothing. The gate, that re-check and the handlers read the work dir the same way (`koda/utils/files.py::file_command_work_dir`), as stored and not stripped, so a work dir whose name ends in a space is the one the grant checks; with no work dir set (or a blank one) the commands refuse to run instead of resolving the path against the process CWD.
