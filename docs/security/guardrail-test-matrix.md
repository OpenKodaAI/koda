# Koda Guardrail Test Matrix

This matrix maps the security boundaries agents rely on to adversarial tests.
Every test in `tests/security/` should prove the expected decision, the
presence or absence of execution, canary integrity, and secret redaction when
the scenario involves credentials or process output.

| Surface | Guardrail | Evidence Target |
| --- | --- | --- |
| Shell | Destructive commands, env exfiltration, reverse shells, and forbidden tokens are blocked before execution. | `tests/security/test_guardrail_adversarial_suite.py::test_shell_destructive_commands_do_not_touch_canary` |
| Background shell | Process handles are scoped to the owning user. | `tests/security/test_guardrail_adversarial_suite.py::test_background_shell_handle_is_user_scoped` |
| File operations | The Telegram file commands (`/cat`, `/file`, `/ls`, `/write`, `/edit`, `/rm`, `/mkdir`) and the agent `file_*` tools share one resolver (`koda/utils/files.py::resolve_work_path`), so a path gets the same decision on both: relative paths resolve against the work directory, never the process CWD; the resolved path, symlinks included, must stay inside the workdir; and secret files stay blocked by name, both for the blocked extensions (`prod.env`, `server.pem`) and for `.env` dotfiles (`.env`, `.env.local`). Committed templates whose final extension is `.example`, `.sample`, `.template` or `.dist` (`.env.example`, `.env.local.example`) are not secrets and stay readable and editable on both, unless they link to a blocked file. The file tools also refuse paths inside a sensitive system directory (`SENSITIVE_DIRS`, matched as written and resolved, so `/var/run` also covers `/run`) unless that directory contains the work dir itself (`koda/utils/workdir.py::sensitive_dir_for`): the work dir and the paths inside it stay usable when the work dir is under one, such as the Docker default `HOME=/var/lib/koda/runtime/home` under `/var/lib`, while a sensitive directory that does not contain the work dir stays refused. The commands skip that check, so the two differ only for a work dir that contains a sensitive directory, such as `/`, where `file_read /etc/hosts` is refused and `/cat etc/hosts` reads the file. `/setdir`, its directory buttons, `agent_set_workdir` and workspace roots all use the same work-dir check (`koda/utils/workdir.py::validate_work_dir`) and refuse a work dir under a sensitive directory; the operator's `DEFAULT_WORK_DIR` is used as configured. `file_grep` skips every blocked file name, does not descend into a sensitive directory that does not contain the work dir, and reads a file symlink only when the full resolver places its target inside the search root, so a link inside a granted subtree to a file elsewhere in the work dir is skipped. A fileops integration grant with `allowed_paths` sees the same resolved path on both surfaces. Each file command takes its path from `koda/utils/files.py::file_command_path` (the first argument for `/write` and `/edit`, every argument joined by a space for the others, never shell-split or unquoted, and `.` for `/ls` alone), and the approval layer (`koda/utils/approval.py::with_approval`) checks the grant on that same path, resolved, before the handler runs; `/file` and `/ls` are gated there like `/cat`, as the read actions `fileops.file` and `fileops.ls`. The file tools pass each `path`, `source` and `destination` as the absolute, symlink-resolved path it names under the work dir (`koda/utils/files.py::work_path_location`). So `/cat src/main.py` and `file_read src/main.py` are both granted under `<work>/src`, `<work>/src/../.git/config` and `src/x /../../.git/config` are refused by both, and `/ls` alone and `file_list` without a `path` are both checked against the work dir. Absolute `allowed_paths` entries (`~` expanded) are compared in their symlink-resolved form, as the call path is (`koda/agent_contract.py::path_in_allowed_paths`, used by both surfaces), so a grant root written through a symlink, such as a symlinked project dir or macOS `/tmp`, still covers the paths below it; a relative entry is compared as written and matches no path. `file_search` and `file_grep` without a `path` are checked against the work dir they read, and `file_move` must have both its source and its destination inside the grant. | `tests/security/test_guardrail_adversarial_suite.py::test_fileops_rejects_symlink_escape_and_sensitive_extensions`, `tests/security/test_guardrail_adversarial_suite.py::test_cat_command_and_file_read_reach_the_same_path_decision`, `tests/test_utils/test_files.py::TestResolveWorkPathMatrix`, `tests/test_utils/test_files.py::TestWorkDirInsideSensitiveDirectory`, `tests/test_services/test_tool_dispatcher_fileops.py::TestWorkDirUnderASensitiveRoot`, `tests/test_services/test_tool_dispatcher_fileops.py::TestDocumentedRelativePathsResolveUnderWorkDir`, `tests/test_services/test_tool_dispatcher_fileops.py::TestEnvTemplatesStayEditable`, `tests/test_handlers/test_setdir_security.py::TestSetdirUsesTheSharedWorkDirCheck`, `tests/security/test_guardrail_adversarial_suite.py::test_cat_command_and_file_read_reach_the_same_grant_decision`, `tests/security/test_guardrail_adversarial_suite.py::test_rm_deletes_only_a_path_the_grant_checked`, `tests/security/test_guardrail_adversarial_suite.py::test_file_and_ls_commands_reach_the_same_grant_decision_as_the_tools`, `tests/security/test_guardrail_adversarial_suite.py::test_cat_and_file_read_agree_on_a_grant_root_written_through_a_symlink`, `tests/test_services/test_tool_dispatcher_fileops.py::TestPathScopedGrantsSeeResolvedFileToolPaths`, `tests/test_services/test_tool_dispatcher_fileops.py::TestGrantRootsWrittenThroughASymlink` |
| Browser | Private-network downloads honor the global kill switch, redirects are blocked before the browser follows them, and uploads follow the shared path policy (`resolve_work_path`): a relative `file_path` resolves against the work dir, and a path outside the workdir or a secret file such as `.env` is refused, as `file_read` refuses it. Like the file commands, uploads skip the sensitive-directory check and keep their reach, anything inside the work dir, also when the work dir is under or contains a sensitive directory (the Docker default `HOME` under `/var/lib`). | `tests/security/test_guardrail_adversarial_suite.py::test_browser_private_download_respects_global_kill_switch`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_download_blocks_private_redirect_before_network`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_upload_rejects_path_outside_workdir`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_upload_refuses_what_file_read_refuses`, `tests/security/test_guardrail_adversarial_suite.py::test_browser_upload_keeps_its_reach_when_the_work_dir_is_under_a_sensitive_root` |
| HTTP/SSRF | Agent web tools, the link analyzer, artifact ingestion, and the control-plane link preview (`koda/services/http_client.py`) only reach public unicast addresses unless a private-network grant (`allow_private_network`) applies: private, loopback, link-local, unspecified (`0.0.0.0`, `::`), reserved, multicast, and `100.64.0.0/10` shared space are blocked, and IPv4-mapped / NAT64 IPv6 addresses are judged by the IPv4 address they embed. The connection is pinned to the validated addresses by a connect-time resolver, so DNS rebinding between the check and the connect cannot reach a private host, and every redirect (including web search) is re-checked before it is followed. Fake-IP DNS setups (Clash, sing-box or Surge in fake-ip mode answer from `198.18.0.0/15`) and CGNAT or Tailscale destinations (`100.64.0.0/10`) are therefore treated as non-public: such a deployment sees `private/reserved` errors until it uses real DNS or grants private-network access. The link analyzer never hands a user URL to yt-dlp, which resolves DNS and follows redirects outside this guard: only URLs whose host is YouTube are treated as videos, and yt-dlp receives a `https://www.youtube.com/watch?v=<id>` URL built from the validated video ID. | `tests/test_services/test_http_client.py::test_fetch_url_cannot_reach_local_service_via_unspecified_address`, `tests/test_services/test_http_client.py::test_fetch_url_pins_connection_against_dns_rebinding`, `tests/test_services/test_http_client.py::test_fetch_url_blocks_redirect_to_unspecified_address`, `tests/test_services/test_link_analyzer.py::TestYtDlpOnlySeesCanonicalYoutubeUrls`, plus MCP HTTP redirect tests below. |
| OpenAI-compatible providers | A provider base URL that is neither operator-overridden nor flagged `allow_private_base_url` must pass the same address check; its connections use the connect-time resolver and do not follow redirects, so an unfollowed 3xx is reported as an HTTP error. | `tests/test_services/test_openai_compatible_runner.py::TestProviderRequestsStayOnPublicAddresses` |
| MCP HTTP | Remote MCP transports reject private/internal hosts during construction and on redirects. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_http_redirect_to_private_destination_is_blocked` |
| MCP stdio/custom | Custom command/env registration rejects obvious host-code-execution escapes and malformed argv values. | `tests/test_services/test_custom_mcp_registry.py` |
| MCP control plane | Agent connection overrides cannot smuggle unsafe commands, malformed argv, unsafe URLs, forbidden env names, non-string env values, or null-as-secret values into runtime config. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_agent_connection_rejects_unsafe_overrides`, `tests/test_control_plane_mcp.py::TestMCPAgentConnections::test_null_env_values_are_ignored_not_stored_as_literal_secret`, `tests/test_control_plane_mcp.py::TestMCPAgentConnections::test_env_values_reject_non_string_values` |
| MCP capabilities | Blocked resources are hidden whether policy stores the URI or the canonical URI hash. | `tests/security/test_guardrail_adversarial_suite.py::test_mcp_resource_blocking_accepts_uri_or_hash_policy_names` |
| Execution policy | Unknown tools fail closed, read-only tasks deny writes, approval grants replay only the authorized action. | `tests/security/test_guardrail_adversarial_suite.py::test_execution_policy_unknown_tool_fails_closed_with_evidence`, existing `tests/test_services/test_execution_policy.py` |
| Provider/runtime env | Tool subprocess env is allowlisted and fails safe if the security RPC is unavailable. | `tests/security/test_guardrail_adversarial_suite.py::test_tool_subprocess_env_drops_secret_canary` |
| Policy engine | Ingest/spend wrappers have explicit tests for deny, hard stop, and the configured outage fallback behavior. | Existing `tests/test_policy_engine_client.py` |

When a new agent-facing tool or MCP capability is added, update this document
in the same change as the policy/test coverage.
