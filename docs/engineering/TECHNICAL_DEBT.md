# Technical Debt and Defect Register

Review snapshot: 2026-11-14. Scope: Python runtime and control plane, Rust sidecars, web app, deployment, CI, tests and docs.

This register consolidates 14 subsystem reviews and one runtime smoke run against a local stack. It describes the code as it was at review time and claims no fixes. Line numbers drift as the code changes, so search for the symbol when a line no longer matches.

- Part 1, the defect register, has 219 entries merged from 239 reported defects.
- Part 2, the technical debt register, has 197 entries merged from 244 reported items.
- Simplification opportunities: ranked list at the end.

## How to read this

**Severity:** `critical` (core feature broken for everyone) > `high` > `medium` > `low`.

**Category order (sort order within a severity):** `security`, `data_integrity`, `correctness`, `reliability`, `performance`, `accessibility`, `ux`, `build`.

**Verification status:**

| Status | Meaning |
|---|---|
| `confirmed` | Reproduced by a probe, script or test, or traced end to end by the reporting reviewer, and kept as confirmed in consolidation. |
| `observed_at_runtime` | Seen in the running stack (browser, curl, logs) during the smoke run. |
| `uncertain` | The finding itself hedges ("likely", "possible", "may"). Reproduce it before scheduling work. |
| `unverified` | Comes from code reading or from one reviewer's own probe, and nobody re-checked it independently. Probably real, but check it before acting. |

**Source codes:** `core` core execution and providers, `tools` tools/MCP/sandbox, `sched` runtime/scheduling/services, `cp` control plane, `mem` memory and knowledge, `multi` multi-agent and skills, `state` state/RPC/Rust, `web-shell` web shell and design system, `web-a` / `web-b` web feature areas, `devops` DevOps/security/supply chain, `tests` tests and quality, `scope` product scope and docs, `smoke` runtime smoke run.

**Debt decisions:** `keep` (accept as is), `repair` (fix in place), `simplify` (same job, less machinery), `consolidate` (merge parallel implementations), `replace` (swap for a standard or different approach), `remove` (delete).

**Effort:** `S` is under a day, `M` is a few days, `L` is a week or more.

## Review notes

- **Merging.** Duplicate findings were merged, and every merged entry lists all of its sources. A merged entry keeps the highest reported severity and the strongest verification status. Merged debt entries take the larger effort estimate.
- **Severity raised by merging.** D-004, D-034, D-083, D-116 and D-126.
- **Categories reassigned.** The smoke-run findings were all filed under `reliability`. The reviewer gave each one a real category.
- **Status set to `uncertain`.** D-068, D-103 and D-217 were downgraded because the original finding hedges.
- **Conflicting reports:**
  - D-098: one report says failed bot-gateway updates are replayed. Another shows that PTB catches handler exceptions, so failed updates are acknowledged and not replayed.
  - TD-001: the reports give different counts for `.env.example` coverage.
- **Reviewer probes left unverified.** Several `unverified` entries cite the reviewer's own probe, for example D-026, D-073 and D-087. They stay `unverified` until a second check.
