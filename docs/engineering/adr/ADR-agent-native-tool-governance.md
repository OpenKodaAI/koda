## 2. Decision

### 2.1 Invariants

1. **Koda policy is the only authority.** A provider built-in tool runs only at a level the agent's signed, published policy pre-authorises, lowered by every ceiling that applies, and only on a provider whose capability the published policy covers. Nothing raises it.
2. **Per-call approval exists only on the governed path.** Built-in tools have no approval state, because the CLIs run headless. Anything that needs a human goes through `<agent_cmd>`, `evaluate_execution_policy` and the approval pipeline (§2.9).
3. **Koda confines model-directed code.** Every process that runs code the model controls, or code it can plant, runs inside Koda's confinement or does not run. A provider's own sandbox is an inner layer, used only where it has been proven to start inside the same confinement.
4. **Never wider than the inner layer allows.** Koda never asks a provider sandbox for more than the effective level, except where Koda's own L2 enforces the level instead. In `RUNTIME_CONFINEMENT=off` the provider's own restriction is the only layer, and no level is weaker than today's behaviour.
5. **The model cannot reach control-plane secrets.** No process the model can reach holds or can read the master key, the bootstrap code, the worker's secrets, another agent's data or an unauthenticated control endpoint. Residuals, including everything `off` gives up (R-8), are listed in §2.5.4.
6. **Fail closed.** An unverified CLI version, a missing flag, an unproven restriction, a settings warning or a missing kernel feature makes the capability unavailable, and the reason is shown. It never silently widens.

### 2.2 Governance model

#### 2.2.1 Field

- `execution_policy.provider_builtin_tools.level` is an ordered enum: `none < read_only < workspace_write < workspace_exec`. It is a typed block compiled at spawn, not a matched rule. There are no per-provider overrides and no free-form tool lists; those break across CLI versions.
- **Default `read_only`.** A missing block or key means `read_only`. It matches the governed path's baseline, where reads by enabled tools are allowed and writes need approval (`services/execution_policy.py:532-575`), and reads stay cheap.
- **One delivery channel.** The published, signed `AGENT_SPEC_JSON` (AG-10a, AG-11) carries the execution policy **and the model policy**. `AGENT_EXECUTION_POLICY_JSON` and its readers are deleted. The worker reads neither drafts nor live control-plane rows for governance. AG-10a moves the execution policy. AG-21b moves the model policy and the chat-settable `providers` keys (`agent_settings.py:232-236`), in the same merge that makes chat commands publish (§2.2.3): the worker's runtime settings view (`_effective_agent_runtime_settings`, `agent_settings.py:232-260`) is computed in `app` from the agent's published snapshot and the install's global settings, and returned by `GET /internal/agents/runtime-settings` on the AG-17 token; the worker keeps its 5 s cache of the answer. AG-11 moves the `skills/_runtime.py` draft fallback. AG-22 moves the four squad paths that read another agent's draft through `get_agent_spec` to that agent's **published** snapshot: the planner (`coordinator_engine.py:423`), the `squad_coordinator_elect` tool (`tool_dispatcher.py:4937`), the coordinator service's eligibility check (`squads/coordinator.py:166-173`, which reads `tool_policy`) and membership's capability hints (`squads/membership.py:214`). They read it through `GET /internal/agents/{agent}/published-spec` on the AG-17 token. `app` reads the target's published version (and, from AG-11, verifies its MAC) and returns a closed field list: `model_policy`, `tool_policy.allowed_tool_ids`, and the spec fields `build_capability_summary` reads. The target must be the token's own agent or an agent in its squad. Neither route reads a draft, and the worker reads no `cp_agent_config_versions` row. AG-22 also moves the `runtime_endpoint_json` write out of `build_draft_snapshot` (`manager.py:12509-12513`) into `publish_agent`, so building a spec writes nothing and the worker role can lose its write on `cp_agent_definitions` (M1-E2-T5).
- **One resolver**, `koda/services/provider_builtin_tools.py`: `normalize`, `validate`, and `resolve(published, provider, ctx) -> BuiltinToolProfile{requested, effective, clamps[], capability, process_class, refusal}`. The runtime, publish validation, the prompt preview and the simulator import it. The control-plane normalizer delegates this block to it.
- The name avoids "native tools", which means Koda tools sent as function-calling schemas (`docs/architecture/tool-registry-native-tools.md`).

#### 2.2.2 Schema

Authored by the operator, in the draft and the published spec:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "koda:execution_policy.provider_builtin_tools",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "level": { "enum": ["none", "read_only", "workspace_write", "workspace_exec"], "default": "read_only" }
  }
}
```

- Validation errors use the existing execution-policy error shape: `{"path": "execution_policy.provider_builtin_tools.level", "code": "invalid_enum", "message": ...}`, and `code: "unknown_key"` for any other key.
- The block has no version key. It is versioned with the snapshot; an incompatible change would add a new key, never a new meaning for `level`.

**Actor.** One shape everywhere (the gate's parameter, the governance block, the audit event):

```json
{
  "$id": "koda:actor",
  "type": "object",
  "additionalProperties": false,
  "required": ["kind", "id"],
  "properties": {
    "kind": { "enum": ["operator", "system", "system:migration", "system:import", "telegram_user"] },
    "id": { "type": "string", "description": "operator account id, Telegram user id, or the system component (supervisor, bootstrap, runtime_snapshot, AG-21 migration, legacy import)" }
  }
}
```

Derived at publish by `publish_agent` (never authored; a draft that contains it is rejected), inside the signed snapshot:

```json
"governance": {
  "provider_builtin_tools": {
    "level": "workspace_write",
    "capability_ceiling": ["read", "write"],
    "providers": ["claude", "gemini"],
    "published_by": { "kind": "operator", "id": "7" },
    "confirmed": true,
    "published_at": "2026-11-20T10:00:00Z",
    "previous_version": 41
  }
}
```

`providers` is every provider the published model policy lets the agent run: the default provider, the fallbacks and the functional defaults. `capability_ceiling` is the union of `capability(provider, level)` over them (§2.2.3).

#### 2.2.3 Capability, escalation and the publish gate

**Capability.** The contract table records, per pinned CLI version, provider and level, a conservative capability set over `read` (file reads), `write` (workspace writes), `exec` (model-chosen programs) and `egress` (model-chosen network connections), taken as the widest over the confinement modes:

| Provider | `none` | `read_only` | `workspace_write` | `workspace_exec` |
|---|---|---|---|---|
| Claude | `[]` | `[read]` | `[read, write]` | `[read, write, exec, egress]` |
| Codex 0.169.0 | `[]` | `[]` (clamped to `none`, §2.3.3) | `[read, write, exec]` (only under `off`, R-8; clamped to `none` under L2) | `[read, write, exec, egress]` |
| Gemini | `[]` (no workspace directory, no tree, no climb, §2.3.2) | `[read]` (plus the startup and JIT GEMINI.md of R-7, and the symlinked GEMINI.md of R-1) | `[read, write]` (with the same two GEMINI.md residuals) | `[read, write, exec, egress]` |

**Escalation** is a publish whose level is higher than the baseline's, or whose `capability_ceiling` is not a subset of the baseline's. Adding Codex to a Claude `workspace_write` agent adds `exec` and is an escalation; raising the level is one; adding Codex to a Claude `read_only` agent is not, because Codex has no tools at `read_only`.

**Runtime check (S10).** A turn on provider P at effective level L runs only if `capability(P, L)` is a subset of the published `capability_ceiling`. Otherwise P is refused for the turn with `capability_not_confirmed`, the fallback chain skips it, and an alert is raised. Between AG-21 and AG-21b the worker still reads the draft model policy, as it does today (C9). In that window S10 is what keeps a provider added by a chat command from running at a capability nobody confirmed. From AG-21b on, the model policy comes only from the published snapshot, so the ceiling covers every provider it names, and capability is monotone in the level. S10 can then fail only after a CLI bump changes the capability table, or through a bug, and it stays as that assertion. Internal calls run at `none`, whose capability is empty, so they pass on any provider. A version without a governance block has the ceiling `capability(its providers, read_only)` (step 2).

**Publish gate.** `publish_agent(agent_id, *, actor, confirm_escalation=False, change=None)` takes a required `actor` (§2.2.2). It is a compare-and-swap on the version number, because the control-plane store has no multi-statement transaction: every `fetch_one`, `fetch_all` and `execute` takes its own pooled connection and autocommits (`koda/state/control_plane_store.py:60-97`; `koda/state/primary.py:330-388`), and `with_connection` replays statements one by one (`control_plane_store.py:106-120`).

- The gate reads the last published version `P` (its number and snapshot). With no lock held, it builds the source, validates it and computes the baseline from `P` (steps 1 to 3).
- Step 4 writes in one short transaction on one connection: version `P+1`, `desired_version = P+1`, the apply operation and the `agent.provider_builtin_tools_changed` event. It uses AG-07's transaction helper (§2.6).
- A concurrent publish of the same agent that wrote `P+1` first makes the insert fail on `UNIQUE (agent_id, version)` (`koda/knowledge/v2/postgres_backend.py:1362-1371`), and nothing of this attempt is written. The gate then re-reads the last version and runs steps 1 to 4 once more: a chat patch is re-applied to the new last published snapshot, and the check runs against the new baseline.
- An operator escalation is retried only when the capabilities it adds are the ones the operator confirmed. Otherwise, or when the second attempt also loses, the publish fails with `publish_conflict` and writes nothing. The route answers 409, and the modal or the chat reply asks to try again.

A chat patch is therefore always applied to the latest published snapshot and checked against the latest baseline; it can never republish an older snapshot over an operator's newer one (§5.1.10). Nothing is locked while the draft is built, so the build's own write to `cp_agent_definitions` (`manager.py:12509-12513`, until AG-22 moves it) cannot wait on the gate.

1. **Source.** Only an `operator` publish takes the draft as it is. No other actor can publish the operator's pending policy:
   - `telegram_user` applies only its own `change` to the **last published snapshot**. The change is a field-level patch from a closed list:
     - `voice_policy.mode`;
     - `model_policy.default_provider`, `model_policy.default_models.<provider>` and `model_policy.functional_defaults.<function>`;
     - `providers.elevenlabs_default_voice`, `providers.elevenlabs_default_language`, `providers.kokoro_default_voice` and `providers.kokoro_default_language`. These voice keys carry no capability.

     The same patch is written to the draft, so the dashboard shows it.
   - `system` publishes only an agent that has **no version at all** (supervisor reconcile, and bootstrap before AG-21b). It takes the draft with `execution_policy` and `tool_policy` replaced by the defaults a new agent gets: no rules, level `read_only`, the secure-default tool subset. The dashboard shows the operator's policy as pending until an operator publishes it. A `system` publish of an agent that has any row in `cp_agent_config_versions` is refused with `system_publish_of_published_agent`. It is never retried with secure defaults, so resetting `desired_version` to 0 cannot republish the draft.
   - `system:migration` publishes the last published snapshot with only the governance block or the signature added (AG-21, AG-11). `system:import` publishes the imported legacy configuration at level `read_only`, which only lowers what those agents ran with.
   - **Validation follows the source.** Each actor validates only what it publishes. `operator` runs `publish_checks` on the draft, as today (`manager.py:12569-12572`). `system` runs it on the draft with the secure-default policies, and `system:import` on the imported configuration. `telegram_user` is validated by the settings route's value checks on its patch, and nothing else. `system:migration` republishes a snapshot that is already published and runs no validation beyond the gate. So draft-only errors (an enabled general provider whose CLI is missing, a granted secret that no longer exists, a runtime prompt-budget overflow, a missing `AGENT_TOKEN`, C9) block only operator publishes and the first `system` publish, never a chat change, the AG-21 record or the AG-11 re-sign (§5.1.10).
2. **Baseline.** The last published version's governance block. A version without a governance block (published before AG-21) reads as `{level: read_only, capability_ceiling: capability(its providers, read_only)}`, for every actor, for S10 and for the resolver. That is what a missing block already means (§2.2.1), so no "unrestricted" baseline exists and no publish waits for a migration. An agent never published has the baseline `{level: read_only, capability_ceiling: [read]}`.
3. **Check.** On escalation, refuse unless `actor.kind == operator` and `confirm_escalation`. The error names the new capabilities. For `telegram_user` the reply is "A troca precisa de confirmação no painel: {capacidades}.", and the patch stays in the draft.
4. **Write** the version `P+1`, the governance block (signed with the snapshot, AG-11), `desired_version`, the apply operation and the `agent.provider_builtin_tools_changed` event (§2.6.1), in one transaction on one connection. A unique-constraint conflict is retried once as described above. The publish fails if the event cannot be written.
5. **The AG-21 migration is a record, not a precondition.** At control-plane start (next to `ensure_master_key`, `supervisor.py:223`), for each agent whose last published version has no governance block, it publishes that snapshot with the explicit block at `read_only` and writes one event with `reason: migration`. Nothing waits for it: an agent it has not reached already runs at `read_only` (step 2), and any publish of that agent works. A failure leaves the health reason `governance_migration_failed:<agent>` and is retried at the next control-plane start; an operator publish of that agent writes the block and the event itself.

**Where publishing runs.** `publish_agent` and signing run only in `app` (the control plane and its supervisor).

- From AG-11 on, the snapshot signer is built only by the control-plane process. `publish_agent` without it raises `publish_requires_control_plane`, and the supervisor refuses a version row that carries no valid MAC (§2.5.3). A worker-side call can therefore never produce a version that runs (A-P-07).
- AG-11 depends on AG-21b, so no release ever signs in a worker.
- The runtime-snapshot fallback publish is deleted from `_resolve_runtime_snapshot` (`manager.py:12633-12636`). A missing version raises `no published snapshot` (`:12637-12638`), and the supervisor skips that agent, so nothing is published.

**Chat settings through the control plane (AG-21b).** Telegram updates reach the worker, so the worker forwards chat settings changes to a broker route on the control-plane API:

- `POST /internal/agents/settings-change` is authenticated by the AG-17 per-worker token. The agent always comes from the token, never from the body.
- The body is `{"telegram_user_id": int, "patch": [{"path": <one of the closed list>, "value": …}]}`. The control plane validates each value: a provider it knows, a model in that provider's catalog for the function, a voice it knows. It checks that the asserted Telegram user is on the agent's allowed-user list as the control plane resolves it, the same check as the approval relay (§2.9.2).
- In one call the control plane writes the patch to the draft and calls `publish_agent(agent, actor={"kind": "telegram_user", "id": <user>}, change=patch)`. That publish applies the patch to the last published snapshot, runs the gate and signs.
- The route answers `published` (with the version), `needs_confirmation` (with the capabilities added; the patch stays in the draft) or `refused` (with the reason). The worker turns the answer into the chat reply.
- Every chat setter uses the route: the voice toggle, the voice and audio defaults, `/provider`, `/model`, the functional defaults, the settings-menu buttons (`callbacks.py:262, 288, 1403`), and the natural-language parser that every plain message passes first (C9).
- Session state follows the answer. `callback_model` changes the session's provider model and turns `auto_model` off (`callbacks.py:266-267`); the worker does that, and any other per-session change a setter makes, only on `published`. On `needs_confirmation` or `refused` the session keeps its provider and model.
- The worker then reads the model policy and the `providers` voice keys only from its published snapshot.

- **Why the workspace is not the cwd.** Gemini reads workspace settings only from the cwd, and starts its `.env` search there (§1.2). With a Koda-owned cwd, a planted or repository-supplied `.gemini/settings.json`, `.gemini/.env` or `.env` in the workspace is never read, whatever its content (`context.includeDirectories`, hooks, MCP servers, discovery commands, telemetry, a base URL or a system prompt).
- **Why the cwd holds a stop file.** Gemini's search does not stop at the cwd. It walks every ancestor up to `/`, loads the first `.gemini/.env` it finds, and sets every key in it that is not already set (§1.2). The cwd's ancestors are:
  - the spawn home, `provider-homes/<agent>/spawns` and `provider-homes/<agent>`;
  - Koda's runtime root and everything above it. On native installs after AG-12 the runtime root is `~/.koda-runtime/<bid>`, so the ancestors include the operator's own HOME. `~/.gemini/.env`, where Gemini users keep personal keys, would then flow into every agent's run. In compose they include `/var/lib/koda/runtime` (`docker-compose.yml:57`), on the `koda-runtime` volume that `runtime-kernel` mounts read-write (`:250`).
  
  Under L2 no confined process can write any of these directories. Under `off`, and before AG-14, an unconfined class M process could plant a file there that changes every agent's Gemini at every level, and that no spawn home removes. The pins do not prevent this, because they are a denylist. Any unpinned variable loads: `CODE_ASSIST_ENDPOINT` (the OAuth endpoint) and `GOOGLE_GENAI_USE_VERTEXAI` did in the probe (§1.2), and by the same code path so would `GOOGLE_APPLICATION_CREDENTIALS` or `HTTPS_PROXY`. So every spawn home gets an empty `cwd/.gemini/.env`. The search finds it in the first directory it examines and reads nothing else, in every confinement mode (verified: no ancestor or home file loaded, no warning). The exposure is new with this design: today's runner does not trust the workspace, so Gemini reads only whitelisted auth keys, and only from a plain `.env` (`chunk-VFM6AETN.js:37777, 38173-38178`; `findEnvFile` checks `.gemini/.env` only when trusted). The pins stay as defence in depth. `GEMINI_CLI_HOME` is pinned because a planted `.env` can set it and move every Gemini path (§1.2).
- **No host system settings.** `GEMINI_CLI_SYSTEM_SETTINGS_PATH` and `GEMINI_CLI_SYSTEM_DEFAULTS_PATH` point under `/dev/null`, which can never exist, so nothing has to keep the path absent. A root-owned `/etc/gemini-cli/settings.json` on the host would otherwise sit above Koda's user settings in the merge order (§1.2). Missing system files are skipped silently, so this pin prints nothing.
- **Why trust comes from the env.** Headless Gemini refuses an untrusted cwd. `--skip-trust` trusts only after the first settings load, so trust would change within a run when the 10 s settings cache expires (§1.2). `GEMINI_CLI_TRUST_WORKSPACE=true` makes every load see the same trusted cwd, which holds nothing but the stop file.
- **Fail closed on settings.** Gemini prints `Invalid configuration in …`, drops the bad key and keeps running (§1.2), so a warning seen at spawn time comes too late to stop a run that has already started without that restriction. The check therefore runs before any spawn. At each worker start, per CLI fingerprint, A-K-05 loads **the exact settings file Koda writes for each level** (for each `security.auth.selectedType` value Koda writes) and requires no warning; Koda writes only a settings file whose SHA-256 A-K-05 has loaded cleanly. The stderr check at spawn time (A-G-09) stays as a backstop: a line `Invalid configuration in` or `Security Warning: Skipping` kills the process and fails the turn. Gemini 0.68.0 also accepts an unknown key silently (§1.2), so a later pin that renamed `tools.core` or `hooksConfig.enabled` would drop that restriction without any warning. A-K-05 therefore also runs a per-key probe: each key of the user settings below, written alone with the wrong type, must print `Error in: <key>`. If any key stops erroring, Gemini is unavailable. The `telemetry.*` keys are not in the per-key probe, because the `telemetry` object is strict and a wrong type and an unknown key print the same `Error in: telemetry` (§1.2); for telemetry the env pins are the control (they take precedence over the settings), and a renamed telemetry key would make Koda's own file print that error in the load probe above. **Compile rule.** `IP(mode)` is the inner-sandbox probe `codex sandbox -c sandbox_mode="<mode>" [the row's workspace-write keys] -- <python> -c <probe>`, run **through the same launcher and confinement profile as the spawn** (`koda-sandbox-exec` with the Codex profile under L2; directly under `off`). It passes when the probe exits 0, a write outside the writable roots fails and a socket fails. It runs at worker start, is cached per CLI fingerprint and profile, and is shown in health and in the spawn event. `L2` means confinement status `enforced` or `filesystem_only` (§2.4). An inner sandbox mode is selected only when its `IP` passed in that profile (A-X-10).

|---|---|---|

Codex at `none` is class S; with a shell it is class M.

**`none` is proven per model, offline.** Codex at `none` is available for a model only when the contract records, for that model and pin, both halves of A-K-04, run against the local stub (§1.2):

- **offered:** the first request's `tools` hold no `exec_command`, `write_stdin`, `view_image` or `collaboration.*` tool, while `exec_command` is present at the shell levels as a positive control;
- **refused:** the stub answers with forced calls, one per run: `exec_command`, `write_stdin`, `shell`, `shell_command`, `local_shell_call`, `view_image`, and `apply_patch` (as a custom tool call and as a function call) adding a file inside and outside the workspace. At `none` each is refused or ignored, no file appears, and the outside canary never reaches a request. At the shell levels, the calls of the tools the model is offered (`exec_command`, and `apply_patch` where offered) run, as the positive control.

A real model rarely calls a tool it was not offered, so a live check proves little about refusal; the forced calls prove it for whatever a model sends. The `apply_patch` refusal is part of the proof, so `gpt-5.5`, Koda's default model, is covered. A model whose first request carries no `tools` array (the code-mode models, §1.2) cannot be checked this way and is `unproven`; none is configured today (`koda/config.py:278-287`). The §5.3 per-model live check stays as evidence that the real provider behaves like the stub; it is not part of the availability rule.

#### 2.3.5 Persistent instructions and extensions

A model with write access, or a shell, can plant files that a later spawn loads automatically. Koda closes the places where that happens:

- **Provider homes are per spawn** (revision 5; revision 6 adds the incarnation, the records, the sweep and the copy rules). Each CLI process gets its own home, created empty for that spawn at `<RUNTIME_EPHEMERAL_ROOT>/provider-homes/<agent>/spawns/<incarnation>/<spawn id>/` (0700). `<incarnation>` is a random id the worker draws at start, and `<spawn id>` is random. The home is removed when the process has exited. HOME, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME` and `XDG_*` point into it. Koda writes into it only what that spawn needs, before the CLI starts, and only named files cross in or out:

  | Provider | Koda writes for the spawn | Copied in before the run | Copied out after the run |
  |---|---|---|---|
  | Claude | a minimal `.claude.json`; `system.md` (§2.3.1) | for `--resume ID`, `projects/<slug>/<ID>.jsonl` from the agent's session store (`[V]`: enough to resume, §1.2); `.credentials.json` (file OAuth only) | `projects/<slug>/<session>.jsonl` of the session id the run reports, into the session store (Bash at `workspace_exec` can rewrite it, R-7); a refreshed credential file, when the write-back rule allows it (§2.4.4) |
  | Codex | `config.toml` with the developer instructions and the §2.3.3 settings | `auth.json` (file OAuth only) | a refreshed `auth.json`, when the write-back rule allows it (§2.4.4) |
  | Gemini | `.gemini/settings.json`; `cwd/` (0500) holding only the empty stop file `cwd/.gemini/.env` (0400, in a 0500 `.gemini/`) | `.gemini/oauth_creds.json`, `.gemini/google_accounts.json` (file OAuth only) | refreshed credential files, when the write-back rule allows it (§2.4.4) |

  **How a file crosses.** The worker, which is unconfined, does every copy, so it must not follow anything the model planted in a home it was granted:
  - The source is opened component by component from the source root's directory fd with `O_NOFOLLOW` (`openat`), the last component with `O_NOFOLLOW|O_NONBLOCK`. It is accepted only if `fstat` shows a regular file with one link, within a size limit (64 KiB for a credential file, 64 MiB for a transcript).
  - The content is written to a new file created with `O_EXCL|O_NOFOLLOW` (0600) in the destination directory, fsynced, and renamed into place there. A content copy is used even within one volume, so a planted link or hard link is never moved into the session store; the credential check-in crosses volumes anyway (`koda-runtime` to `koda-state`).
  - The destination directories are Koda-created and granted to no confined process.
  - Claude's session id, as the run reports it, names a file only if it is a bare UUID (`^[0-9a-f]{8}(-[0-9a-f]{4}){3}-[0-9a-f]{12}$`; 2.1.325 uses one, `[V]`). Koda computes `<slug>` from the cwd as 2.1.325 does (each `/` becomes `-`, `[V]`) and never reads it from the home.
  - Anything else copies nothing, and the audit event `provider.spawn_copy_refused` records the reason (§2.6.2; `[V]` for the mechanism, §1.2).
  - Copy-in needs the same care only for the source: its destination is the new, empty home before the CLI starts.

  Everything else a CLI writes (Codex's SQLite state and memories, Claude's `.claude.json` backups and plugin store, Gemini's `tmp/` and trust files, C18), and anything a model plants (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `settings*.json`, `skills/`, `rules/`, `hooks.json`, extensions, `.env`), goes with the home. Therefore:
  - no spawn reads what another spawn wrote. Two concurrent spawns of one agent, at different levels and with different users' instructions and memory context, each see only their own instructions, settings and cwd (A-H-01; `[V]` at the CLI level for Codex and Gemini, §1.2). Under L2 each CLI process is granted only its own spawn home (§2.4.2), so a `workspace_exec` shell cannot rewrite the home of a concurrent turn (§5.3);
  - there is no allowlist rebuild that could miss a file, and nothing deletes a file under a running spawn;
  - the only per-agent provider state is the Claude session store, `<RUNTIME_EPHEMERAL_ROOT>/provider-homes/<agent>/claude-sessions/`, which only the worker reads and writes and no CLI process is granted. Concurrent turns of one Claude session each resume from the stored copy, and the last to finish replaces it, so the file is never interleaved (today both write in the one shared home);
  - credential files are copied in under the per-provider lock, and written back only by the rule of §2.4.4.

  **Orphaned spawns.** A killed worker is now routine: every published chat change restarts it, and the kernel SIGKILLs it after 15 s (C17). Its CLIs run in their own session, so they can outlive it, and their homes hold the instructions, the memory context and the credential copies. So:
  - When the worker starts a CLI, it writes a record `provider-homes/<agent>/spawn-records/<incarnation>/<spawn id>.json`: the CLI's pid and its start time (`/proc/<pid>/stat` field 22). No confined process is granted `spawn-records/`.
  - At worker start, before its first spawn, the worker handles every record and home of another incarnation. The kernel runs one worker per agent and reaps the old one before it spawns the new one (C17), so none of them belongs to a live worker. If the recorded pid is running with the recorded start time, the worker sends SIGKILL to that pid's process group (the CLI is its own group leader); a pid reused by another process is left alone. It then removes the home and the record.
  - Nothing crosses out of an orphan: its transcript and credential copies are discarded (an interrupted task is re-queued and replays, C17).
  - When it starts each spawn, the worker also removes any home of its own incarnation that no live spawn owns (a removal that failed earlier). A removal failure is logged as `spawn_home_removal_failed` and retried at that point.
  - A-H-02 tests this.

  The homes are not placed under the task tmp, as REV's round-4 review suggested: governed shell and git are granted the task tmp read-write under L2 (§2.4.2), so a background shell of the same task could plant files in the next spawn's home there. A spawn home is granted to that one CLI process only, and so is Claude's system prompt file inside it (§2.3.1).

- **Workspace customisation** is not loaded:
  - Claude: `--safe-mode` (CLAUDE.md, skills, plugins, hooks, MCP, commands, agents) and `--restricted` (project settings).
  - Codex: `project_doc_max_bytes=0` (workspace AGENTS.md), skills off (workspace `.agents/skills` and `.codex/skills` included), `--ignore-rules`, the reviewed feature set, and no `--trust`, so the workspace `.codex/config.toml` is not loaded (all `[V]` offline, §1.2).
  - Gemini: the workspace is never the cwd, so its `.gemini/settings.json` and `.env` files are never read; the stop file ends the `.env` search at the cwd, so no ancestor's `.gemini/.env` is read either; `memoryBoundaryMarkers: []` stops the GEMINI.md search at each workspace directory, so no ancestor's GEMINI.md is read; the host's system settings are pinned away; extensions off by `--extensions=none`; hooks, skills, sub-agents and MCP off in the user settings; the workspace GEMINI.md as described in §2.3.2.
- **Host-level CLI configuration** (O-10). Gemini's system settings are pinned away (§2.3.2). Claude applies admin-managed settings even under `--restricted` and `--safe-mode`, and Codex reads `/etc/codex/*.toml` (§1.2). L2 grants `/etc` read-only, so no confined process can plant these files. Under `off`, a Koda running as root could plant them, and then they would affect every agent (R-8). AG-23 and AG-24 record whether a pinned path or a flag excludes each file, and add each to the canaries.

Executable customisation (hooks, MCP servers, plugins, extensions, rules, skills, discovery commands) would run code at `read_only` and must stay off for the levels to mean anything. Instruction files (CLAUDE.md, AGENTS.md, GEMINI.md) only steer the model; turning them off removes a feature users may rely on. Both are operator question OQ-3. If the operator keeps instruction files, Claude omits `--safe-mode` and Codex omits `project_doc_max_bytes=0`; Gemini needs no change, because it loads the workspace-root GEMINI.md at `read_only` and above in any case (§2.3.2). Residual R-7 then applies to all three. Executable customisation stays off for Claude without `--safe-mode`: `--restricted` ignores the settings files that define hooks and enable plugins, a spawn home starts with no installed plugins, `--disable-slash-commands` turns off skills and commands, `--strict-mcp-config` turns off MCP, and custom agents need the Agent tool, which is never in `--tools` (`[I]`, covered by the live canaries).

Live canaries (§5.3) cover each crossing file and each discarded item, in the workspace and in the spawn home. For Gemini they also cover every ancestor of the cwd, with a canary variable that is not pinned and a canary GEMINI.md.

At risk: the master key, the previous key and `bootstrap.txt`; the worker env (DSN, S3 secret, granted secrets, runtime tokens); other agents' workspaces, homes and sessions; kernel RPC, the sidecars and publish integrity.

#### 2.4.2 Layers

- **L0 Placement** (host-independent):
  - `koda-state` is mounted only in `app` (AG-19). The master key, the previous key and `bootstrap.txt` never enter `runtime-kernel`, and the key never moves.
  - Worker data moves to a new `koda-worker-state` volume (`WORKER_STATE_ROOT`), mounted in both `app` and `runtime-kernel`; every C14 consumer resolves through it in both processes. The supervisor forwards `WORKER_STATE_ROOT` instead of `STATE_ROOT_DIR` (`supervisor.py:92`).
  - CLI login homes move off `koda-runtime` to the app-only path (§2.4.4).
  - No Koda state or temporary file lives in a directory other users or agents share: `RUNTIME_EPHEMERAL_ROOT` defaults to `~/.koda-runtime/<bid>` (mode 0700) on native installs instead of the system temp dir, the compose kernel root moves to `/var/lib/koda/runtime/kernel`, and Docker MCP env files are written into a 0700 per-worker directory and deleted once the container has started (AG-03, AG-12).
- **L1 Process hygiene:** AG-04 (implemented) makes the worker and the kernel non-dumpable with no cores. One allowlist builder makes every child env, with no DSN, S3 secret, granted secrets, runtime, kernel or broker token; it sets HOME and the `XDG_*` directories to the child's own home and `TMPDIR` to the task tmp; this covers MCP and media spawns (AG-03). Prompts stay off argv, because `/proc/*/cmdline` stays readable even under Landlock `[I]`.
- **L2 OS confinement.** One Rust primitive, `rust/koda-runtime-kernel/src/confinement.rs`, exposed as the `koda-sandbox-exec` binary in the existing crate (no new service, ADR-001):
  - It applies `no_new_privs`, then a Landlock filesystem ruleset, then at ABI ≥ 4 TCP rules (connect only to `RUNTIME_CONFINEMENT_EGRESS_PORTS`, default `443,53`, plus the port of the provider's configured base URL; no bind), then at ABI ≥ 6 signal and abstract-UNIX-socket scoping, so a confined process cannot kill the worker or the kernel or reach their abstract sockets. Then it execs.
  - Landlock's ptrace restriction stops reads of the unconfined worker's and kernel's `/proc/<pid>/environ` and `mem`, and of sibling domains, on every ABI.
  - It exits 126 if any requested right cannot be enforced. Nesting only narrows. A process inside it cannot change mount topology, which is why Codex's bubblewrap sandboxes cannot start there (§1.2).
  - **What it does not cover:** TCP rules are per port, so the allowed ports reach every host, and an internal service listening on 443, 53 or the provider port is reachable; UDP is not restricted (DNS and other UDP egress stay open); connecting to a pathname UNIX socket is not a Landlock right. So under `strict` the kernel listens on TCP only, and a UNIX-socket kernel target is refused at start (M1-E6-T1 constraint, §9.3).
  - Both spawn paths exec through it: worker-side spawns through `koda/security/process_confinement.py` (AG-14), and kernel `StartTask` and `ExecuteCommand`, whose profile the kernel computes itself (AG-15).
  - A workspace grant is refused when the work dir is, or contains, a shared or Koda-owned directory: `/tmp`, `/var/tmp`, `/dev/shm`, the system temp dir, HOME, a state root, `RUNTIME_EPHEMERAL_ROOT`, `RUNTIME_KERNEL_ROOT`, a provider home or a login home (AG-12 predicate, checked again by AG-14).

  Allowlist (anything else is denied, including worker-state, the artifact root, `/app`, `/workspace`, shared HOME, other agents' workspaces and homes, the login homes, and the `tmp_images` root):

  | Grant | Provider CLI | Governed shell and git | MCP stdio | Media tools | Chromium |
  |---|---|---|---|---|---|
  | read-only: `/usr`, `/lib*`, `/bin`, `/sbin`, `/etc`, `/opt`, `/proc`, required `/dev` nodes; `CODEX_BIN`/`GEMINI_BIN` must resolve inside these | yes | yes | yes | yes | yes |
  | read-write: task tmp | yes | yes | yes | yes | yes |
  | workspace | read-only at `none` and `read_only`, else read-write | read-write | only if the server declares it | no | no |
  | own spawn home, read-write (Gemini's `cwd/` inside it is mode 0500); never another spawn's home, the Claude session store or `spawn-records/` | yes | no | no | no | no |
  | other | — | — | server package read-only; state dir read-write | input read-only; output dir read-write | browsers path read-only; profile read-write |

- **L3 Provider layer (inner):** Claude `--restricted --safe-mode` and its tool lists; Codex's reviewed feature set and, only where `IP` proved it inside the same profile, its inner sandbox; Gemini's `tools.core` and user settings. Spawn homes live under `<RUNTIME_EPHEMERAL_ROOT>/provider-homes/<agent>/spawns/<incarnation>/<spawn id>/`, one per CLI process, created empty and removed after it, and swept with any orphaned CLI at the next worker start (§2.3.5). A work dir is never HOME and never contains a provider home or a state root, checked by path component; this also applies to `agent_set_workdir` (`tool_dispatcher.py:1404-1416`) and to internal calls (S7).
- **L4 RPC:** kernel RPC authentication (M1-E6-T1) is a prerequisite for AG-15, which adds per-worker kernel tokens: the kernel binds each `StartTask` and `ExecuteCommand` to the token's agent and computes the floor itself (that agent's workspace, one spawn home under that agent's `provider-homes/<agent>/spawns/<incarnation>/`, and the task tmp); a caller profile can only narrow it; a request without a profile is rejected. The control-plane worker broker (AG-17) has its own per-worker token.

**Compose** (`docker-compose.yml`, `packages/cli/release/bundle/docker-compose.release.yml`, `packages/cli/release/CHECKSUMS.txt`): AG-19 removes `koda-state` from `runtime-kernel` and adds `koda-worker-state` to both services. AG-19b adds `security_opt: [no-new-privileges:true]`, `cap_drop: [ALL]` and, after the smoke test, `read_only: true` with a tmpfs `/tmp`. #### 2.4.4 Provider credentials and login homes

- **Env credentials** where the provider supports a non-rotating token (API keys, Claude's long-lived `setup-token`): delivered in the CLI env by the allowlisted builder; nothing is written to the home.
- **File OAuth** (Claude `.credentials.json`, Codex `auth.json`, Gemini `oauth_creds.json` and `google_accounts.json`; the same names D-230 deletes, `manager.py:1575-1580`):
  - The canonical login homes move from `koda-runtime` (`docker-compose.yml:29-31`, mounted read-write by `runtime-kernel` at `:250`) to `STATE_ROOT_DIR/provider-logins/<provider>` on `koda-state`, which becomes app-only with AG-19. Class T login flows run with that HOME. The move copies and verifies; the old copies go one release later (AG-32). Operator question OQ-4.
  - Every spawn works on its own copy (AG-13a). Before the spawn the named credential files are copied into the spawn home (0600, by the copy rules of §2.3.5). Until AG-13b the worker copies from and to the canonical login home, which it can already read and write today. From AG-13b it checks the files out through the AG-17 broker (`POST /internal/provider-credentials/{provider}/checkout`, per-worker token) and checks them in afterwards. Config, hooks and instruction files never cross, because nothing else is transferred.
  - **Write-back only from a spawn whose model could not write the copy.** The spawn home is granted read-write to the CLI process (§2.4.2), so at a shell level the model can rewrite the credential copy, with a later expiry or another account's token, and a write-back would put it into every later spawn of every agent on that provider. A refreshed copy is therefore written back only from a spawn at `none` or `read_only` on any provider, or at `workspace_write` once AG-23 (Claude) or AG-25 (Gemini) proves that its write tools write only the workspace. It is never written back from a shell level: `workspace_exec`, or Codex `workspace_write` under `off`. Until a provider's compiler lands (AG-23 to AG-25), every spawn of that provider still runs today's bypass mode (C1 to C3), in which the model can already rewrite the shared login home (C13). In that window AG-13a writes back as the shared home behaves today, with the checks below, which is no less restrictive than today (§6). The rule above applies from that provider's compiler on.
  - **Checks on every write-back.** The named files only, each parsed against a per-provider schema: known keys, the size limit, the same account id as the canonical copy, and an expiry later than the canonical copy's. The write happens under the per-provider lock. AG-13a's worker-side write-back runs these checks itself, and from AG-13b the control plane runs the same checks at check-in. Concurrent eligible spawns each hold a copy, so two refreshes at once leave the newer one in place. The account and expiry checks guard against a CLI bug, not the model, which cannot write the file at an eligible level. A copy from a shell-level spawn, or one that fails a check, is discarded, and the audit event `provider.credential_writeback_refused` records the reason (§2.6.2).
  - **What a shell level gives up.** A refresh made during a shell-level spawn is lost. On a provider that rotates refresh tokens and revokes the old one, the canonical copy then stops working, and the provider has to log in again. Whether each pinned CLI rotates, and whether rotation survives per-spawn copies with concurrent spawns of one agent and of several agents, needs live evidence (O-4). Env credentials (API keys, Claude's `setup-token`) do not refresh and are recommended for agents at shell levels. If rotation does not survive, file OAuth modes require env credentials under confinement. The per-spawn copy and the shell-level rule change how production credentials are handled, so they wait for OQ-4 (§9.1).

### 2.5 Secrets and the master-key boundary

#### 2.5.1 Key handling (AG-05, implemented)

- Only `app` holds the key: the control plane and the supervisor.
- No process creates a key implicitly. `ensure_master_key()` runs at supervisor start (`supervisor.py:223`) and ends in `fresh_install`, `upgrade`, `lost_key_reset`, `verified` or `rotation`; anything else refuses to start with operator guidance (C10). On upgrade, the control plane refuses to start when the key decrypts none of the newest stored values, unless the operator writes the new key's fingerprint prefix to `.master.key.accept-undecryptable` next to the key; that file is removed once used.
- The acknowledgement file and the previous-key file sit next to the key on `koda-state`; with AG-19 they become app-only with it. `CONTROL_PLANE_MASTER_KEY_PREVIOUS` is an `app` env value and never reaches a worker (AG-03).
- The fingerprint outcome audit event is `security.master_key_fingerprint_recorded`.
- ADR-026: the relocation step is superseded; the volume stops being mounted in `runtime-kernel`, the key stays put. Rotation (M5-E6-T11) and backups (M2-E6-T1) are unchanged.

#### 2.5.2 Workers never decrypt (AG-17, AG-21b, AG-22, AG-11; checked at AG-19)

- Static granted secrets are still decrypted by the control plane into the spawn env.
- Dynamic needs go through internal broker routes on the existing control-plane API:
  - MCP connection env, and MCP OAuth access tokens (refresh and write-back in the control plane only);
  - the squad peer bot token, for an agent in the token agent's own squad only, which the squad admin check, posting as a peer's bot and a peer bot's username use (C10);
  - the ElevenLabs key and voice catalog, and the image-generation key;
  - CLI credential checkout and check-in (§2.4.4) and approvals (§2.9.2);
  - from AG-21b, chat settings changes and the runtime settings (§2.2.3, §2.2.1);
  - from AG-22, the published-spec read for squad peers (§2.2.1).
- The agent-directory reads (`list_agents`, `get_agent`, and `dashboard_service._agent_catalog`, C10) become `agent_directory()` (AG-17). It is a manager read that returns each agent's id, display name, squad and workspace names from `cp_agent_definitions` and the workspace and squad maps. It builds no default-model summary and no draft snapshot and does no seeding, so it touches no secret. It needs no broker route, because the worker already reads those rows and none of them is secret.
- **The property and its owners.** "Workers never decrypt" means that no call a supervised worker can make reaches `decrypt_secret`, `encrypt_secret` or `get_signing_key` (§5.1.4). Each path in C10 names the item that removes it. AG-19 removes the key only after all of them (its Deps), and its acceptance runs the whole-worker check (§5.1.4 (c)), so removing the key breaks no feature.
- **What is the boundary, and what is not.** The reachability check guards that functional property against regressions; it is not a security boundary. Code running in the worker process, such as in-process plugin code (R-3), can import any module in the image, whatever the entrypoint imports, and until AG-19 it can read the key file directly (C10). The boundary is the key's absence from `runtime-kernel` (AG-19). From then on, `decrypt_secret` raises `MasterKeyUnavailable` in every worker (`crypto.py:159-168`), and the ciphertext the DSN can reach is useless without the key. M1-E2-T5 narrows what the DSN can reach.
- Route auth: a per-worker token, minted by the supervisor at spawn, stored as a hash in Postgres (ADR-011), bound to `agent_id`, rotated on respawn, rate-limited; every resolution is audited by id, never value. The token never enters a child env (AG-03), the worker is non-dumpable (AG-04), and L2 denies ptrace and `/proc/<worker>/environ` and `mem` to every confined process (D12-14).
- ADR-025 clarification: "workers resolve secret references at start" means resolution by the control plane, into the spawn env or through the broker.

#### 2.5.3 Snapshot integrity (AG-11)

- Published snapshots are HMAC-signed with the ADR-025 HKDF signing key (M1-E6-T3). The MAC covers `agent_id`, `version`, `published_at` and the SHA-256 of the canonical snapshot JSON (governance block included).
- The supervisor verifies before building a worker env: the MAC, that `agent_id` and `version` in the MAC match the row and the agent being spawned (so another agent's signed snapshot is refused), and that the version is not lower than the highest version it has verified for that agent since it started (rollback while `app` runs is refused). On a failure it does not spawn and emits `security.snapshot_rejected`.
- **Only `app` signs.** The signer is built only by the control-plane process, and `publish_agent` without it raises `publish_requires_control_plane`. AG-11 depends on AG-21b, so by the time snapshots are signed, no chat path publishes from a worker (§2.2.3).
- Versions published before AG-11 carry no MAC. At control-plane start, AG-11 republishes each agent's unsigned latest version unchanged and signed (actor `system:migration`, through AG-21's actor-aware primitive, which never reads the draft), trusting the row as it is at upgrade, as today. It runs no draft check (§2.2.3 step 1), so an invalid draft cannot stop it. If it still fails for an agent (a database error, or no signing key), the supervisor does not spawn that agent's unsigned version: health shows `snapshot_unsigned:<agent>`, the re-sign is retried on every supervisor reconcile pass (every `CONTROL_PLANE_POLL_INTERVAL_SECONDS`, `supervisor.py:433`), and an operator publish of the agent also produces a signed version.
- **What the MAC protects, and from when.** It stops a holder of the owner-role DSN who cannot compute the signing key. Until AG-17 (workers stop loading the master key to decrypt) and AG-19 (`koda-state` leaves `runtime-kernel`) both ship, a worker can read the key material and forge a MAC (R-5).
- A DSN holder can still, across an `app` restart, delete newer version rows or point `desired_version` at an older signed version (`manager.py:12600-12607`; `supervisor.py:459`). That is residual R-5. M1-E2-T5 closes it, with its scope extended by this ADR: the worker role gets no write on `cp_agent_config_versions` or `cp_agent_definitions`, which is possible once AG-21b has moved every worker publish to `app` and AG-22 has removed the endpoint write from `build_draft_snapshot` (C9). A persisted high-water mark was rejected: restoring an older database backup would then refuse every agent.
- Live worker reads of `cp_mcp_tool_policies` (`services/execution_policy.py:127-165`) move into the snapshot (O-5).

### 2.6 Audit

Events go to the existing sinks (`control_plane/audit.py:22`, `services/audit.py`). Governance events (2.6.1 and the approval events) are written in the transaction of the action they record, and the action fails if they cannot be written (a `required=True` path in `record_audit_event`). The control-plane store has no multi-statement transaction today (every call autocommits on its own connection, §2.2.3; `record_audit_event` too, `audit.py:44`). So AG-07 adds a one-connection transaction helper to `koda/state/control_plane_store.py`, which runs a list of statements on one pooled connection inside one database transaction, as `koda/squads/threads.py:195` already does with its own pool. The `required=True` path writes through the caller's transaction.

### 2.8 Defaults, migration and rollback (MISSION §13)

#### 2.8.1 Defaults and existing agents (AG-21, AG-30)

- **Changed (AG-02, implemented):** `CODEX_BIN` and `GEMINI_BIN` are each one executable path. A command line reports `unavailable:unverified_cli_version`; a missing binary `unavailable:cli_not_installed`.
- **Changed defaults (AG-12):** native `RUNTIME_EPHEMERAL_ROOT` moves from the system temp dir to `~/.koda-runtime/<bid>`; compose `RUNTIME_KERNEL_ROOT` moves from `/tmp/koda-runtime/default/kernel` to `/var/lib/koda/runtime/kernel`. Both hold only ephemeral task files; Claude sessions kept for `--resume` start fresh after the move.
- **New:** `RUNTIME_CONFINEMENT`, `RUNTIME_CONFINEMENT_EGRESS_PORTS`, `WORKER_STATE_ROOT` and `AGENT_WORKSPACE_ROOT`, each in `config.py`, `.env.example` and the docs.

#### 2.8.3 Installs, work dirs and rollback

- **Existing installs (AG-18, AG-19):** the release compose and CHECKSUMS are updated. #### 2.8.4 Operator migration notice

**Release note and `docs/operations/upgrade.md` section (English):**

> ### Provider built-in tools now follow Koda policy (ADR-002)
>
> Claude Code, Codex and Gemini CLI no longer run with their own approvals turned off. Until this release Claude ran with `bypassPermissions`, Codex with `danger-full-access`, and Gemini in `yolo` mode, so an agent's provider could edit files and run commands without any Koda approval.
>
> **What changes when you upgrade**
>
> - Every agent gets the new setting **Provider built-in tools**, set to **Read only**. On upgrade Koda publishes a new version of each agent from its last published version, so pending drafts are not published. The report `koda policy audit`, which you can run before upgrading, lists the agents that used the provider's own edit or shell tools.
> - At **Read only**, Claude and Gemini can read files in the agent's workspace and do nothing else. **Codex has no read-only mode: at None and Read only it answers without any tools (no shell, no file reads).** With confinement on (the default), Codex gets tools only at **Workspace exec**; with confinement off, also at **Workspace write**. Below Workspace exec, Koda uses only the Codex models it has verified for the installed Codex version; system health lists any configured model that is not verified.
> - Edits and commands through Koda's own tools (files, shell, git) still ask for approval per call, and work for agents whose policy allows them once M3-E3-T1 is approved.
> - Raising an agent to **Workspace write** or **Workspace exec**, or adding a provider that gains capabilities at the agent's level (for example Codex on an agent at Workspace write), needs a confirmation in the dashboard.
> - Chat settings changes are now published right away. This covers the commands (`/provider`, `/model`, the feature-model, voice and voice-model commands), the buttons of the Telegram settings menu, and plain messages that ask for such a change (for example "mude o provedor para codex"). Each one publishes only its own change and no other pending dashboard edit. A change that would add capabilities is refused in the chat and waits in the dashboard for confirmation; the conversation keeps its current provider and model.
> - **Each published chat change restarts the agent.** A reply in progress gets up to 15 seconds to finish and is then stopped. Unfinished and queued messages run again after the restart, under the new settings. Each restart counts against the queue's recovery limit (`QUEUE_MAX_RECOVERY_ATTEMPTS`, default 3): a message interrupted by more restarts than that is moved to the dead-letter queue instead of running again. Once approvals move to the database (M3-E3-T2), pending approvals expire on restart and must be requested again; until then they are restored as before. Voice changes already worked this way.
> - **Model, provider and voice changes saved in the dashboard take effect when you publish.** Until this release, a saved draft change to these settings could reach the running agent as soon as someone opened a settings command or menu in the chat.
> - Provider CLIs no longer load hooks, MCP servers, plugins, extensions, skills or rules from the workspace or from their home directory, and no longer load CLAUDE.md or AGENTS.md (subject to operator approval, OQ-3). Gemini also ignores the host's `/etc/gemini-cli` system settings and any `.gemini/.env` file in the directories above its working directory, including `~/.gemini/.env` on native installs. Put Gemini keys in the dashboard's provider connection instead. Gemini no longer loads GEMINI.md files from the directories above the workspace. At **Read only** and above it still loads the GEMINI.md at the workspace root when it starts, and adds the GEMINI.md files between a file it reads and the workspace root; Gemini 0.68.0 has no setting to turn this off. At **None** Gemini sees no workspace content at all. A GEMINI.md in the workspace that is a symbolic link is followed, so do not let untrusted content put links into a Gemini agent's workspace, and prefer scoped API keys.
> - Each provider run gets a new, empty home directory. Only logins and Claude's conversation history carry over between runs. Logins you made in the dashboard keep working. A login refresh that happens during a run at **Workspace exec** is not saved, because the agent's own commands could have changed it. If a provider then asks you to log in again, use an API key for agents at that level (subject to operator approval, OQ-4).
> - Starting an agent directly with `python -m koda --agent-id`, without the control plane's supervisor, still works for published agents, but that process runs outside the confinement boundary (it decrypts provider keys itself). Use it only for development. In the Docker deployment it no longer works inside `runtime-kernel`, which no longer holds the master key.
> - `CODEX_SANDBOX` and `CODEX_APPROVAL_POLICY` are no longer read. > - On native installs, Koda's runtime files move from the system temp directory to `~/.koda-runtime`; Claude sessions start fresh once.
> - The control plane refuses to start when the master key does not match this database. If the original key is lost for good, follow `docs/operations/backup-restore.md` (the `.master.key.accept-undecryptable` file).
> - Model-directed processes run under Linux Landlock confinement (`RUNTIME_CONFINEMENT=strict`). ### 2.9 Governed path: per-call authorisation (D-011) and cross-process approvals (D-012)

M3-E3-T1 and M3-E3-T2 implement this section. The flow is ADR-009's: decision, then request, then a fingerprinted grant, then execute.

#### 2.9.1 D-011: `ExecutionAuthorization`

- **Object.** A frozen dataclass in `koda/utils/approval.py`: `agent_id`, `task_id`, `tool_id`, `command_digest` (SHA-256 of the exact command string, or of the git argument string), `work_dir`, `basis` (`policy_allow | human_grant | operator_command | scheduled_job`), `rule_id`, `grant_id`, `snapshot_version`, `nonce`, `expires_at` (mint time plus the call's timeout).
- **Minted** only by `authorize_call(evaluation, call, ctx, grant=None)`, called in `_execute_tool_traced` after the policy decision (`tool_dispatcher.py:732-770`):
  - `deny` → never;
  - `allow` → `policy_allow`, with the matched `rule_id`;
  - `require_approval` or `allow_with_preview` → only with a grant consumed through the control plane for this call (§2.9.2) → `human_grant`;
  - supervised mode: a write call (`_is_write_tool`) needs `human_grant` even when the rule allows it, which replaces the contextvar check at `tool_dispatcher.py:779-790`;
  - dry run and the S2 to S6 ceilings keep refusing writes (`tool_dispatcher.py:791-799`).
- **Passed explicitly**, never through a contextvar: `_execute_tool_traced` passes it as a keyword to the handler; only the shell, `shell_bg` and git handlers accept it and pass it to `run_shell_command(…, authorization=)`, `bg_process_manager.start(…, authorization=)` and `run_cli_command_detailed(…, authorization=)`.
- **Checked and consumed** by those runners: `agent_id` equals `AGENT_ID`, `tool_id` matches, the digest and the work dir equal the values they are about to run, it has not expired, and its nonce is unused (an in-process set). Anything else returns "Error: command execution not authorised." and logs `execution_authorization_refused`.
- **No ambient state.** `_execution_approved` and `check_execution_approved` are deleted. `asyncio` copies a context into every task it creates, so a contextvar set around `execute_tool` would leak into `shell_bg`'s task and any other task spawned meanwhile. The background task holds nothing it could reuse.
- **Human commands and scheduled jobs** mint their own: `with_approval` and `dispatch_approved_operation` mint `operator_command` for the typed command (`koda/handlers/commands.py:984, 1010`; `koda/handlers/packages.py:36, 62`), and the scheduled shell job mints `scheduled_job` from the published job definition (`scheduled_job_runtime.py:299-305`).
- **Governed git cannot execute repository config (AG-03, AG-12).** `git_status`, `git_diff` and `git_log` are read tools that run without a grant (C16), so a file planted in `.git/` must not turn them into exec:
  - every git process Koda spawns (the governed `git_*` tools through `cli_runner`, worker-side git in `queue_manager.py` and `runtime/controller.py`) runs with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `-c core.fsmonitor=false -c core.hooksPath=/dev/null -c core.pager=cat`, and `--no-ext-diff --no-textconv` where the subcommand takes them;
  - before it runs, Koda reads the repository's own config with `git config --file <gitdir>/config --no-includes --list` (which runs nothing) and refuses when a key is outside an allowlist (`core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`, `core.ignorecase`, `core.precomposeunicode`, `core.autocrlf`, `core.eol`, `remote.*.url`, `remote.*.pushurl`, `remote.*.fetch`, `branch.*.remote`, `branch.*.merge`, `branch.*.rebase`, `user.name`, `user.email`, `init.defaultbranch`, `extensions.objectformat`); the error names the key, so `filter.*`, `diff.*.textconv`, `core.sshCommand`, `include*` and the like are refused;
  - governed file tools refuse writes to any path with a `.git` component; provider built-in writes under `.git/` are a live check below `workspace_exec` (§5.3), and a CLI that allows them stays class M.
- **The per-agent enable is the published execution policy; no new field.** The secure default denies `shell_execute`, `shell_bg` and `git_*` (C5), so governed shell and git stay off until the operator publishes a rule that allows or asks for them. Only an operator publish can carry such a rule (§2.2.3, step 1). M3-E3-T1's choice "enable for the listed agents, or a per-agent enable that defaults to off" therefore means publishing rules for the listed agents (from `koda policy audit` section 3) or not.

#### 2.9.2 D-012: one request and grant store, written only by the control plane

- **Tables** (registry migration, BIGINT ids, agent scope):
  - `approval_requests`: `id`, `agent_id`, `worker_incarnation`, `origin` (`agent_call | operator_command`), `task_id`, `session_id`, `chat_id`, `tool_id`, `call_fingerprint`, `scope_fingerprint`, `description`, `preview_text`, `risk_class`, `status` (`pending | approved_once | approved_scope | denied | expired`), `created_at`, `expires_at`, `resolved_at`, `resolved_by_kind`, `resolved_by_id`, `resolution_reason`.
  - `approval_grants`: `id`, `request_id`, `agent_id`, `session_id`, `chat_id`, `kind` (`once | scope`), `fingerprint`, `max_uses`, `uses`, `expires_at`, `issued_by_kind`, `issued_by_id`, `mac`, `created_at`.
- **One writer.** Only `app` writes either table, through one module, `koda/control_plane/approvals.py`. The worker calls internal routes with its per-worker broker token (AG-17); `agent_id` always comes from the token, never the body:
  - `POST /internal/approvals/consume` with `tool_id`, `call_fingerprint`, `scope_fingerprint`, `session_id`, `chat_id` and an optional `request_id`. In one transaction (AG-07's one-connection helper, §2.6) the control plane looks for a usable grant for the token's agent: a `once` grant for that `request_id` whose fingerprint is the call fingerprint; otherwise a `scope` grant whose fingerprint is the scope fingerprint and whose session and chat match (as today, `approval.py:1371-1389`). It locks it, verifies its MAC, `agent_id`, `uses < max_uses` and `expires_at > now()`, increments `uses`, writes `approval.grant_consumed`, and returns `{grant_id, kind}`; with no usable grant it returns `404 no_grant`. The worker mints `human_grant` only from a success.
  - `POST /internal/approvals` creates a request (`expires_at = now + APPROVAL_TIMEOUT`, 300 s, `approval.py:80`), sends `NOTIFY approval_requested`, and returns its id; the worker then shows the Telegram card.
  - `POST /internal/approvals/{id}/telegram-decision` relays a Telegram button press (Telegram user id, decision, scope).
- **Order for every call that needs a grant:** consume first (an existing scope grant covers the call with no request and no card); only on `no_grant`, create a request and show the card; after the resolution, consume with the request id.
- **Resolution** has one function, `resolve_approval_request(request_id, decision, scope, resolver)`, used by the dashboard route (operator session; it replaces `approval_broker`'s in-memory resolve) and by the Telegram relay. In one transaction (the same helper) it writes the status, inserts the grant with `mac = HMAC(signing key, canonical(id, request_id, agent_id, session_id, chat_id, kind, fingerprint, max_uses, expires_at, issued_by))` using the ADR-025 signing key (M1-E6-T3), writes `approval.resolved`, and sends `NOTIFY approval_resolved` with the request id.
- **Waiting.** The worker waits on `approval_resolved` through the one reconnecting LISTEN implementation (ADR-011, `koda/agents/listen_notify.py`), with a 5 s poll of the request status as the fallback, until `expires_at`; then it consumes.
- **Single use and expiry.** Allow once is `max_uses = 1`, and the consume transaction makes concurrent uses impossible. Scope grants keep the existing `ApprovalScope` TTL and `max_uses` (`approval.py:1413-1414`).
- **Restart.** At each worker spawn the supervisor marks that agent's `pending` requests from another incarnation `expired` (`approval.expired`, reason `worker_restart`). Nothing is restored, so D-163 disappears. Grants persist until they expire (ADR-009).
- **The boundary, stated exactly.**
  - The Telegram relay is a resolution the **worker asserts**. Telegram updates reach the worker, and a callback query carries nothing the control plane can verify; it checks only that the request belongs to the token's agent and is pending, and that the asserted Telegram user is on that agent's published allowed-user list. Any code that holds the worker's broker token can therefore approve that agent's own requests (R-4). The chat settings route (`POST /internal/agents/settings-change`, §2.2.3) is asserted the same way and checked the same way. Its reach is smaller: a patch from the closed list, which the publish gate refuses when it adds a capability.
  - What keeps a prompt-injected model out is that it cannot obtain the broker token: AG-03 keeps it out of every child env, AG-04 makes the worker non-dumpable, and L2 denies ptrace and `/proc/<worker>/environ` and `mem` (D12-14). Before AG-14 and AG-15, a same-uid process during the AG-04 startup window can read it (R-2).
  - The grant MAC stops a grant row inserted directly with the DSN only when the inserter cannot compute the signing key, which holds from AG-17 and AG-19 on; before then a worker can forge it (R-4). That is no weaker than today, where grants live in worker memory and JSON files.
  - Cross-agent use is refused at consume: every row and MAC carries `agent_id`, checked against the token.
- **Retired:** `_PENDING_OPS`, `_PENDING_AGENT_CMD_OPS` and `_APPROVAL_GRANTS` (`approval.py:78-79, 1588`), the restore path (`approval.py:86-153`), and `koda/state/pending_approvals.py` and `koda/state/approval_grants.py` with their JSON fallbacks. Existing file grants are not imported as live grants: they were written by workers and would become MAC-signed grants (§9.3, M2-E1-T2).

## 3. Alternatives considered

| Alternative | Why not |
|---|---|
| **Fewest moving parts.** A boolean in `autonomy_policy`, honoured only in `guarded` mode; the key stays mounted; network unconfined; dashboard approvals proxied to the worker. | Contradicts ADR-002(B) and ADR-009 (which rejects the proxy). Inert for general tasks and dependent on a query-text classifier. *Grafted:* confining worker-side git, the AST spawn guard, the work-dir invariant, supervised stepping in Koda's loop. |
| **Key relocation** to an app-only volume (copy, verify, delete). | Surgery on key material, and a downgrade trap (older releases created a new key when the file was missing). Making the existing volume app-only reaches the same boundary. |
| **Default `none`, with `strict` imposed silently.** | Silently removes reads from Claude and Gemini agents and governed shell on kernels older than 6.7. |
| **Codex `read_only` through L2 only** (inner `danger-full-access`, Koda maps the workspace read-only): revision 1, and option (ii) of S2-2. | Under L2 the shell gets TCP 443 and 53 to every host at `read_only` (HTTPS egress), and under `off` nothing confines it. |
| **Codex's own `--sandbox read-only` for `read_only`** (revision 2). | Cannot start inside Landlock, so under the default modes Codex could run no command and read nothing while the UI claimed reads; unconfined it reads every file the uid can read. |
| **A nested `koda-sandbox-exec` around Codex's shell** (a narrower Landlock domain with no TCP, through `$SHELL` or a wrapper). | Unproven that Codex 0.169.0 runs `exec_command` through a configurable shell; recorded as O-9 for a later pin. |
| **Refuse Codex entirely under `off` when the worker can read the key.** | Codex `read_only` already clamps to `none`, and the confirmed levels show R-8 in the modal; refusing would remove the only Codex modes native installs have. |
| **Gemini per-task system settings file** (revision 2). | Gemini 0.68.0 skips it unless it and every ancestor are root-owned, and ignores `admin.*` from any file (§1.2). |
| **Root-owned static Gemini settings in the image** (option B of R2-3). | Works only in the image, not on native installs, and still needs the workspace out of the cwd; one Koda-written user-settings file in the rebuilt home works everywhere. |
| **`--skip-trust`.** | Trust arrives after the first settings load and the 10 s cache, so the workspace layer and `.env` would load only on later reloads. Env trust with a Koda-owned cwd that holds only the stop file is the same on every load. |
| **`GEMINI_RESTRICTED_MODE=true` with folder trust off** (untrusted cwd, so no JIT GEMINI.md and no `.gemini/.env`). | Undocumented variable; forces `default` mode, so only `none` and `read_only` could use it, giving two trust modes per level. Revisit if OQ-3(b) for Gemini matters. |
| **Gate chat toggles by an engine-simulated widening of shell, git and write decisions** (SEC alternative in S2-4). | Needs a probe-call corpus and a simulate diff on every toggle. Publishing the last published snapshot plus the toggle's own change is smaller and also stops unrelated draft content. |
| **Keep the model policy live** (option (a) of R2-7: carve it out of the signed snapshot and keep S10 as the gate). | Two delivery channels for governance, and the chat command would take effect without any publish or audit. It remains only as the interim state between AG-21 and AG-21b. |
| **Chat commands keep publishing inside the worker** (the worker keeps the signing key and write access to `cp_agent_*`). | The worker could then sign any snapshot, so the MAC would protect nothing against a worker (R-5), and M1-E2-T5 could never deny those writes (R3-1). |
| **The `telegram_user` part of AG-21 waits for AG-17** (REV's first option in R3-1), with the model-policy switch moved into AG-21 (R3-2). | The gate and the migration would then wait for the broker, a high-risk item. Splitting the chat part into AG-21b keeps AG-21 independent and still lands the model-policy switch in the same merge as the chat publish, which is what R3-2 asks for. |
| **Apply chat changes without restarting the worker** (hot reload). | A second delivery channel next to the signed spec. The restart already happens for the voice toggle today, and tasks survive it (C17). |
| **Stop the Gemini `.env` search in the home** (`<gemini home>/.gemini/.env`, REV's option in R3-4). | It also works (verified). The cwd's stop file is chosen because the cwd is the first directory searched, so the search never looks above the cwd and does not rely on HOME being the cwd's parent. |
| **Pin every variable Gemini reads from `.env`.** | A denylist that misses each new variable a version adds (S3-1). The stop file makes the search read nothing. |
| **Keep the Gemini system settings path absent by the rebuild** (REV's wording in R3-4). | A path under `/dev/null` can never exist, so nothing has to keep it absent. |
| **Refuse the `system` publish inside the runtime-snapshot fallback** (SEC's recommendation in S3-4). | Deleting the fallback is smaller, because no caller needs it: the supervisor and bootstrap already publish a never-published agent first. The general rule, that a `system` publish of an agent with versions is refused, still covers the reconcile path. |
| **Disable `instant_interrupt`.** | It adds no tool, process or authority, and it does not change the model-visible input (§1.2). Keeping the default avoids changing Codex's interrupt behaviour without evidence. |
| **Close the Claude transcript residual** by checksumming transcripts between turns, or by replaying instead of resuming after a `workspace_exec` turn. | A checksum cannot tell Claude's own appends from an edit Bash makes during the same run. Replay after every `workspace_exec` turn costs a full replay to block steering that gives the model nothing beyond its own level (R-7). |
| **Serialise provider spawns per agent** (REV's alternative in R4-1). | An agent with ten queued tasks would run one CLI at a time, and a shared home would still be granted read-write to a `workspace_exec` shell that could plant files for the next spawn. Per-spawn homes cost one directory per spawn. |
| **Per-spawn homes under the task tmp** (REV's location in R4-1). | Governed shell, `shell_bg` and git get the task tmp read-write under L2, so a background shell of the same task could plant files in the next spawn's home. |
| **Keep Codex's developer instructions on argv** (today, `codex_runner.py:171-174`). | `/proc/<pid>/cmdline` stays readable by any process of the same uid, even under Landlock `[I]`, and the instructions carry a user's memory context (C18). A 0600 file in the spawn's own home is private to that spawn. |
| **Link the Claude session store into the spawn home** instead of copying one transcript in and out. | It would grant the CLI the whole store, so a `workspace_exec` Bash could rewrite every session of the agent rather than its own. Copying one named file, by the copy rules of §2.3.5 (no link is followed, the session id is a bare UUID, the slug is Koda's), keeps the store out of every L2 grant and out of reach of a link planted in the home. |
| **A migration that blocks publishing** (`governance_migration_pending`, revision 4). | REV's simpler option in R4-2: a missing block already means `read_only`, so reading a block-less version that way removes the refusal, the "unrestricted" baseline and the per-agent retry, and the migration can never block a publish. |
| **Lock the agent's `cp_agent_definitions` row for the whole gate** (revision 5; REV's second option in R5-2). | The store has no multi-statement transaction, so the lock would be a statement on one connection while the rest of the gate ran on others (§2.2.3). The draft build writes that same row when the endpoint changes (`manager.py:12497-12513`), so the gate would wait on itself for up to `PRIMARY_STATE_BRIDGE_TIMEOUT_SECONDS` (30 s, `koda/state/primary.py:30`) and fail. Making it work needs a connection-scoped transaction layer, the build outside the lock and AG-22 first. ## 4. Consequences

**Positive**
- One authority, one field, one resolver, one delivery channel (execution and model policy), one publish gate, one approval store.
- Child runs, artifact-gap turns, dry runs and internal calls become restricted on every provider; internal calls run with no tools at all, and Codex never runs `danger-full-access` outside L2. No level is weaker than today in any confinement mode.
- Provider switches cannot add a shell or egress without confirmation, and chat toggles cannot publish operator drafts. Workers never publish or sign, so the snapshot MAC holds against them once the key leaves their reach.
- Workspace content cannot configure, extend or redirect a provider CLI.
- Policy-approved governed shell and git can run, bound per call; dashboard approvals work across processes.
- The key and the bootstrap code leave every model-reachable container, and workers stop decrypting.
- Operators can trace who granted what.
- Concurrent turns of one agent cannot read or change each other's instructions, memory context or settings, and nothing a CLI writes in its home outlives the run.

**Negative and costs**
- Coding agents slow down until an operator opts them in; each governed round costs a resume, and Codex and Gemini follow-ups are replayed rather than resumed.
- Under the default confinement Codex has two levels, `none` and `workspace_exec`; a Codex agent at the default level answers without reading the workspace (OQ-6).
- More approvals. Workspace customisation stops loading (OQ-3), except Gemini's JIT GEMINI.md (R-7).
- Every published chat settings change restarts the agent's worker, as the voice toggle already does: a reply in progress is cut after 15 s and re-queued (C17), its CLI is killed when the new worker starts (§2.3.5), and from M3-E3-T2 on pending approvals expire (§2.9.2).
- Codex, governed shell and git need Landlock (kernel ≥ 5.13; ≥ 6.7 for `strict`) for anything beyond `none`.
- One new volume, which backups must include. CLIs must be upgraded deliberately; each bump re-runs the contract test, the feature review, the offline probes and the live checks.
- Every spawn starts from an empty home, so Codex and Gemini lose their local caches between runs, and Claude's transcript is copied in and out on every resumed turn.
- A file-OAuth credential refreshed during a shell-level spawn is not written back (§2.4.4); on a provider that rotates refresh tokens this can log the provider out (O-4, OQ-4 (c)).
- Gemini at `read_only` and above still loads the workspace GEMINI.md (R-7) and follows a symlinked one (R-1).

**Deleted**
- `permission_mode` and `dry_run` from `QueryContext` (`queue_manager.py:630` and its uses), `llm_runner` and every runner.
- `claude_runner._effective_permission_mode` (`:92-96`) and the duplicate argv builder; `gemini_runner._effective_approval_mode` (`:86-96`); the Codex dry-run and resume-in-danger branches (`codex_runner.py:259-260, 283-286, 312-330`).
- The reads of `CODEX_SANDBOX`, `CODEX_APPROVAL_POLICY` and their validator (the stored values in AG-32); `AGENT_EXECUTION_POLICY_JSON` and its readers.
- The `_execution_approved` contextvar, the in-memory approval stores and the approval JSON fallbacks.
- The worker-side decrypt paths (C10); the draft reads (`agent_settings.py:232-236`, `skills/_runtime.py`); the `/var/lib` prefix rule and the HOME fallback for work dirs; the `/tmp` work dir of the memory extractor.
- The unused `sandbox_policy` gates (TD-037) and the bwrap backend; the `KODA_AGENT_DEFAULT_*` claims in `docs/operations/hardening.md`; the "plan" mode concept.
