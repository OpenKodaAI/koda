## 2. How to read this matrix

### Status vocabulary

| Status | Meaning |
|---|---|
| `complete_verified` | Reachable from its entry point; a test run, probe or the runtime smoke exercised the main path and found no defect in it. Gaps listed in the row still apply. |
| `implemented_unvalidated` | Wired and reachable, but the main path was not exercised: tests are mocked, absent or were not run. |
| `partial` | Part of the documented contract works; another part is missing or defective. |
| `ui_not_functional` | The UI accepts input, but the backend ignores it or does not exist. |
| `inaccessible` | Code exists, but no user or runtime entry point reaches it. |
| `broken` | The main path fails: shown by a probe, the runtime smoke, or a concrete code trace. |
| `duplicated_obsolete` | Superseded, duplicated or dead. Candidate for removal. |
| `missing_required` | Required by the product contract, docs or `CLAUDE.md`, and absent. |

### Evidence tags

Each claim in the "Gaps and evidence" column carries the strongest evidence behind it.

| Tag | Meaning |
|---|---|
| [S] | Observed in the runtime smoke (section 3). |
| [R] | Recorded command and result in `VALIDATION_REPORT.md`. |
| [V] | Verified by an auditor: probe, script, simulation or test run. |
| [C] | Code trace or grep. Not executed. |
| [I] | Inferred, plausible or not run. Unverified. |

### Merge and reconciliation rules

- One row per feature. Features reported by several auditors are merged into one row.
- When auditors disagreed, the row takes the lower status in this order:
  `broken` < `missing_required` < `ui_not_functional` < `inaccessible` <
  `partial` < `implemented_unvalidated` < `complete_verified`.
- Runtime smoke [S] and recorded validation [R] override auditor statuses in either direction.
- Every disagreement and override is listed in section 5.
- Cross-cutting presentation defects (i18n, hydration) are tracked on the web shell
  rows (F-WEB) and referenced from the affected feature. They do not lower that feature's status.

### Path conventions

| Prefix | Expands to |
|---|---|
| `cp/` | `koda/control_plane/` |
| `svc/` | `koda/services/` |
| `rt/` | `koda/services/runtime/` (tests: `tests/test_services/runtime/`) |
| `web/` | `apps/web/src/` |
| `tabs/`, `catalog/`, `system/` | `apps/web/src/components/control-plane/{editor/tabs,catalog,system}/` |
| bare `*.tsx` component paths | `apps/web/src/components/` |
| bare `queue_manager.py`, `tool_dispatcher.py`, `llm_runner.py`, `*_runner.py` | `koda/services/` |
| bare Python test names | under `tests/` (find by name); web tests are colocated `*.test.ts(x)` |

Line numbers are as of the audit tree and drift with edits.

## 3. Critical user journeys (runtime smoke)

The smoke ran the Python control plane on the host with PostgreSQL 16 +
pgvector, the Rust security sidecar and the production web build. There was no
Docker daemon, no runtime-kernel, memory, artifact or retrieval sidecar, no LLM
credentials, and egress was limited to package registries. No agent turn could
run. The recipe is recorded with the smoke results; the database it created was dropped.
